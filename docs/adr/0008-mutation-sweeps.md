# ADR-0008: Mutation sweeps on GitHub-hosted runners

## Status

Accepted, 2026-11-18 (operator, Replikanti/interviewscam#40, STOP 1). The Numbers are measured on the acceptance sweeps of the second PR (Replikanti/interviewscam-site#15, 2026-11-19); the first PR's provisional values are replaced. The five decisions of STOP 1:

1. **Acceptance set.** The mutant files of M4 PR 4/4 are not recoverable, so the acceptance runs use new sets of the same shape against today's `main`, plus a census of every suite (part 9).
2. **Two PRs.** The first PR adds `selftest.sh --only`, a registration stub of `mutation-sweep.yml` and this ADR; the second adds the runner and the full workflow, sweeps itself from its own head before it merges, and replaces the provisional numbers.
3. **Twenty shards**, written as 20 literal jobs, with no change to the guard (part 6).
4. **Merge locally.** The agent merges the shard results with `mutate.py merge`; no guard exception for `actions/download-artifact` (part 7).
5. **No local full `check.sh` for this repo.** Agent sessions take the result of the `check` job on the pushed head instead; local records-mode runs stay, because private pushes are metered (ADR-0007 part 6).

Implementation: part 4 and the stub of `.github/workflows/mutation-sweep.yml` (first PR); `tools/mutate.py`, `tools/mutate.sh`, the full workflow, `tests/mutate/` and the measured Numbers (second PR).

## Context

- **Every safety-net PR proves its checks by mutation.** The implementer and QA each patch `tools/sitecheck.py` or `assets/js/search.js` in hundreds of ways and run the fixture suites against every mutant, many of them in Chrome. Until this ADR the sweeps ran on the operator's workstation, inside a 3-core cap that other work shares, with tooling kept in each agent's scratch directory.
- **They were the longest step of a fix round.** Measured on M4 PR 4/4 (Replikanti/interviewscam-site-history#2), fix round 2, 2026-11-11: QA's recheck of 101 static and 97 browser mutants started at 20:05 CET and was still running at 01:32 CET; one browser mutant over 53 reflow rows had not finished after 12.5 minutes, and one `render-report` suite (114 rows then) took 19 minutes on about a third of a core. The CI `check` job ran the same suites on one runner, `render-report` in 89 s and `reflow-search` in about 6 minutes. The implementer's sweep of the same round covered 365 mutants, and its local full `check.sh` runs took 88 to 111 minutes under load, against 11 to 17 minutes on an idle machine.
- **Public runners cost no minutes.** Standard GitHub-hosted runners are free for public repositories, and this repo is public since ADR-0007. The operator approved Replikanti/interviewscam#40 on 2026-11-12 on one condition: the sweeps load GitHub's runners, not the local machine.
- **The workflow hardening limits what a workflow can be** (ADR-0007 part 4): a run step is only `bash tools/<name>.sh [--flag]...` (`RUN_ALLOWED`, so no `${{ }}` in it), `env:` is refused (`EXEC_KEYS`), and `actions/download-artifact` is allowed only in the job `lighthouse` of `lighthouse.yml` (ADR-0003 part 2).
- **The self-test had no selection.** `tools/selftest.sh` ran all of its 4190 rows (run 44222078867 on `main`, 2026-11-18), 1484 s of the 1727 s `check` job, for any mutant.

## Decision

### 1. Sweeps run only on GitHub-hosted runners of this repo

A mutation sweep runs only through `.github/workflows/mutation-sweep.yml`, started with `gh workflow run` on a sweep branch; the local machine only starts the run and downloads its results. No sweep, and no part of one, runs locally.

**Why:** the operator's condition of 2026-11-12, and the data above: one runner gives a browser suite a whole machine, which the shared local cap does not, and the runs cost no minutes. **Rejected:** a local sweep under a lower CPU cap (it breaks the operator's condition, and the 3-core cap already made a recheck run past five hours); sweeps in the private repo (metered minutes, and ADR-0007 part 5 allows exactly three workflows there).

### 2. The runner is std-only Python

The second PR adds `tools/mutate.py`, Python 3.11 or newer, standard library only, run as `python3 -I -B` (ADR-0002 part 3), behind the shim `tools/mutate.sh` that `RUN_ALLOWED` requires.

**Why:** the runner orchestrates: it edits text, starts `selftest.sh`, waits with a timeout, kills a process group and writes TSV. No part is CPU-bound, and the code it has to stay in step with (the row format, the `-I -B` conventions of `tools/sitecheck.py`) is std-only Python. **Rejected:** Rust, which the operator prefers, loses here on three concrete costs: every binary of this repo is pinned by SHA-256 in `tools/pins.env`, so a toolchain would need a pinned download in `fetch-tools.sh`; each of the 20 shard jobs would pay that download plus a cold `cargo build`; and a crate directory would need a `FIXTURE_SKIP` entry. Speed buys nothing in a process that waits on `selftest.sh`. bash loses because overlapping exact-once counting on arbitrary Unicode text, strict JSON and TSV escaping are error-prone in it. Third-party mutation tools (mutmut and cosmic-ray for Python, Stryker for scripts in the browser) bring a pip or registry supply chain (D3 for the registry; this repo has no pip dependency), generate operator mutants instead of the targeted per-branch find and replace mutants the QA rule needs, and none drives a bash self-test with named rows.

### 3. The mutant file

A mutant file is `tests/mutants/<name>.jsonl`, committed on a sweep branch: JSON Lines, ASCII only (so every invisible or look-alike character shows as `\uXXXX`), LF only, a final LF, no blank line, one object per mutant with the keys `id`, `suites` and `edits` and optionally `expect` (exact row names) and `note`. Each edit has exactly `file`, `find` and `replace`; `file` is a tracked regular file at `HEAD` that decodes as UTF-8, in a plain relative form; `find` is not empty and differs from `replace`. `suites` is a non-empty list of distinct suite names (part 4), or exactly `["*"]` for the whole self-test. Duplicate keys, `NaN`, `Infinity` and wrong types are refused. An edit must match exactly once, overlapping matches counted, in the text the earlier edits left; otherwise the mutant is INVALID. A `file` under `tests/mutants/` is refused, because the shard tree does not hold that directory: the shard removes it in a throwaway commit of the tree's own right after `git worktree add` and restores every run to that commit (`drop_mutant_files`), so the code a sweep runs is the swept commit without its mutant files.

**Why:** a committed file is reviewable, passes the public scrub with the rest of the diff, and is tied to the commit the sweep runs. The tree drops the mutant files because the guard's PT2a refuses a multi-line JSON Lines file outside `content/` as JSON front matter (ADR-0007 part 4): sweep branches never run `ci.yml`, but `records-mode` copies the tree's git listing and runs `check.sh --records`, whose guard step met the mutant files, so its control failed in every sweep (census run 44481370238, shard-2; STOP 1 decision 3 rules out a guard change). **Rejected:** a guard exemption for `tests/mutants/` (a path where a record could pass PT2a, and a guard change); another file format or place (one object per line is what makes a mutant reviewable, and every place in the tree meets PT2a); the mutants as a dispatch input (one string, not reviewable, not scrubbed, not tied to a commit); operator mutants generated by a tool (part 2).

### 4. `selftest.sh --only`

`bash tools/selftest.sh --only SUITE[,SUITE...]` runs only the named suites. A suite is the first path segment of the rows a block prints: the token after `ok   ` or `FAIL ` up to `/`, a space or `:` (`render`, `render-report`, `wiring`, `site-intake-expect`); run 44222078867 shows 42 of them, and the first PR adds `selftest-only`. Every fixture case and every later block of rows is guarded by its suite (`selftest_wants`); a runner whose rows belong to two suites prints only the selected ones (`selftest_rows`), its "runner did not finish" check counts only the selected suites' rows (`selftest_ok_count`), so a failure only the partner suite sees stays out of the selection as its row does, and that line names a selected suite (`selftest_suite`). Under `--only` the rows stream to stdout as they finish and `tee`, an ordinary background job reading a FIFO and waited for by its PID, copies them to a log, so a run stopped at its budget has already printed every row it finished. The shell writes to the FIFO write-only, so it is no reader of its own FIFO: when stdout's reader closes early (`| head -n 1`), the run ends with SIGPIPE instead of blocking on a full FIFO. On HUP, INT, TERM or PIPE the trap (`selftest_on_signal`) stops `tee` with SIGKILL (a SIGTERM the run inherited as ignored would not stop it), removes the run's temp directory and raises the same signal again, so a calling script sees a death by signal and stops as it did before (nothing covers SIGKILL). After the blocks the log is checked: a row of an unselected suite, or a selected suite without a row, fails the run with exit 2 (`selftest_selection_check`), so a block that lost its guard, or a misspelt suite, can never pass as a selection. `FAIL:`, `NOT RUN` and detail lines are no rows. The html and reflow invariants hold only for the suites that ran. Usage errors exit 2 before any tool is fetched; a name is `^[a-z0-9][a-z0-9-]*$`, matched against the characters written out, so no locale lets a look-alike, a zero-width character or a newline through. Without `--only` the run and its output are unchanged, and `wiring/selftest-no-args` holds `step_selftest` to `bash "$CHECK_ROOT/tools/selftest.sh"`, so CI never runs a selection.

**Why:** a sweep runs the suites that can kill a mutant, 290 to 482 s for `reflow-search` and 72 to 129 s for `render-report` on GitHub's runners (Numbers), instead of the whole 1484 s self-test for every mutant. The selection is keyed by the row names everybody already reads in the `check` log, so a mutant file names suites the way a QA report names rows. **Weak point:** a mutant killed only by an unselected suite reports SURVIVED. That is the safe direction: every survivor is investigated, and a selection can never turn a survivor into a kill. A suite printed by several blocks (`wiring`, 26 rows) runs all of them; a block that depends on another block's side effects would be partial under selection, which the census (part 9) finds. **Rejected:** selecting by fixture directory (most suites have none); selecting single rows inside the table runners (out of scope for Replikanti/interviewscam#40; a whole suite is cheap enough per mutant, Numbers); a separate test runner beside `selftest.sh` (two copies of every suite drift).

### 5. Controls, verdicts and the TIMEOUT rule

Each shard first runs one unmutated control per distinct suite set of its runnable mutants, in order of first appearance. A control fails on an exit other than 0, any `FAIL` row or a timeout, and then every mutant of the shard is VOID and the shard fails. Each mutant then ends as KILLED (exit 1 with a `FAIL` row; the first failing row is reported), SURVIVED (exit 0, no `FAIL` row), INVALID (an edit does not match exactly once) or TIMEOUT (its run passed the budget B, even after a `FAIL` row). Any other outcome is ERROR, which is no verdict. A timeout never counts as KILLED.

After every run, control or mutant, the shard settles before the next one starts. First no process of the run may be left: the selftest's process group gets SIGKILL, and the runner, a child subreaper (`prctl(PR_SET_CHILD_SUBREAPER)`), inherits every descendant whose parent died, so it kills and reaps its children until none is left (`kill_strays`), including processes started with `setsid` or `start_new_session` (the self-test starts some, which `killpg` never reaches) and ones with a cleared environment. Then the tree goes back to the commit of part 3 (`restore_tree`). Right after that commit the shard records a pristine snapshot (`Pristine`): the git state a run can write that changes what a checkout writes or what a later run's git does (`git_state`: in the common git directory `config`, `info/` with attributes, exclude, sparse-checkout and grafts, `hooks/`, `shallow` and the alternates of `objects/info/`; in the tree's own git directory `config.worktree`, `info/`, `commondir` and `gitdir`; the tree's `.git` file; the replace refs; the global config files, `~/.gitconfig`, `~/.config/git/` and `GIT_CONFIG_GLOBAL`; every entry of the common `objects/` directory with its size, mtime, ctime and inode, `info/commit-graph*` and `info/packs` aside), and every file of the tree with its executable bit and symlink target, read from the disk (`tree_content`). The restore first compares the git state and stops on any change, before it runs git on it (a run that sets `core.autocrlf`, a smudge filter, an attribute, a hook, an fsmonitor command, a replace ref or a global setting). Then it clears every skip-worktree and assume-unchanged bit (with one set, `git reset --hard` leaves a changed file as it is), detaches HEAD at that commit (a run may commit, move HEAD or switch to a branch), resets the index and the files and removes everything untracked or ignored but `.tools/`; every git call of the restore runs with `core.hooksPath=/dev/null`, `core.fsmonitor=false`, no global or system config file, `GIT_NO_REPLACE_OBJECTS` and none of the variables that point git elsewhere, so a setting the snapshot already held cannot act inside the restore either. Last it checks the outcome: HEAD is that commit, every index entry is plain (`H` in `git ls-files -v`), the status is clean, and the tree equals the snapshot byte for byte on disk, so no git setting can make a changed output look clean. The object store is in the snapshot because git does not verify an object's hash when it reads it, and a loose object shadows a packed one of the same name: a run that writes a different body under an existing blob's name leaves the checkout output of that restore intact, but a later run's `git cat-file` reads the forgery (review round 3). Every write changes the ctime, which no process can set back, so a rewrite in place that keeps the name, size, inode and mtime still shows. A clean run only reads the store: the self-test's git writes (the records-mode copies, the guard and records-repo fixtures) all go to repositories of their own in temporary directories, and the census after this change has every control green (run 44572401985, part 9). A mutant run that commits in the shard tree therefore ends as ERROR; it cannot be told apart from one that forges an object. Not snapshotted, because they cannot change what the checkout of a commit writes or a later run reads: loose and packed refs other than `refs/replace/` (the restore names the commit by its hash), the reflogs, and `objects/info/commit-graph*` and `objects/info/packs` (derived indexes that git may rewrite on its own; a wrong one is refused by git or regenerated, it never substitutes an object's content). The toolchain cache `.tools/` is the one part of the tree the restore keeps; it may hold only regular files and directories (`tools_cache_problem`), because a symlinked `.tools/cache` would send the next run's download into a tracked directory, which the content check would see only after that run.

**Trust boundary.** The restore defends the shard tree, its git state and the runner's git configuration against what a mutated script of this repo writes there by mistake or by a bug. It does not defend the runner itself: GitHub-hosted runners give the job passwordless `sudo`, so a run could change `/etc/gitconfig`, `/etc/gitattributes`, the git, bash or Python binaries, or the Chrome the reflow suites start, and no check inside the same job could prove such a change undone. That is accepted, not closed, for three reasons: the code a sweep runs is a reviewed commit of this repo plus a reviewed mutant file (part 3), never third-party input; each shard job runs on a fresh runner that GitHub discards afterwards, so a change cannot outlive the job or reach another shard; and within a shard a mutant that damaged the runner shows in its verdicts and logs, and the double runs of the acceptance sets (part 9) would disagree. A stray still alive after 10 s of the sweep (`STRAY_SWEEP_S`), a changed git state or a failed check makes that mutant ERROR and the rest of the shard NOT-RUN, with the reason in its log (a failed control's shard is VOID). Failing closed rather than repairing the state: a mutant of this repo's code never writes git state, so any change is a fault to read, and a repair would need its own proof per setting. The bits are cleared rather than refused, because a run sets them as it leaves an untracked file: local state of the tree, not of the commit; the checks after the restore make a clearing that did not hold an ERROR instead of a leak.

**Why:** a mutant verdict means something only against a green control on the same runner and commit, and every run starts from that commit with no process of an earlier run alive; a leak (a commit, an index bit, a stray writing to the tree) would carry one mutant's change into the verdicts of the next ones while the shard still reports `complete yes`. A hang is not a detection, because a check that hangs in CI blocks the merge instead of naming the fault. **Rejected:** one control per shard for the whole self-test (1484 s, and a red unrelated suite would void every selection); counting a timeout as a kill (it hides a hang behind a green verdict).

### 6. Sharding: 20 literal jobs

`mutation-sweep.yml` holds the jobs `shard-1` to `shard-20`, identical except their index, which the runner reads from `GITHUB_JOB`. Mutant i of the file (0-based, file order) runs in shard (i mod 20) + 1.

**Why:** the guard allows a run step only as `bash tools/<name>.sh [--flag]...` and refuses `env:`, so a matrix leg could not learn its index without relaxing ADR-0007 part 4; literal jobs need no change to the guard. Round-robin spreads the mutants of each suite over all shards, so a file that lists the browser mutants together still balances. **Rejected:** `strategy.matrix` (above); contiguous blocks (a block of browser mutants would land on one shard); fewer or more shards (Numbers).

### 7. Results and the local merge

Each shard uploads its own artifact `shard-<k>`: `results.tsv` (`id verdict killer expected shard seconds`), `meta.txt` (commit, shard, mutant file and its SHA-256, the controls, the deadline), a copy of the mutant file and one log per control and mutant, and it writes its table to the step summary. After `gh run download`, `python3 -I -B tools/mutate.py merge <dir>` checks that all 20 shards are there, of one commit and one mutant file (content and path), every mutant in its shard, none VOID, NOT-RUN or ERROR and every `expected` value consistent with its verdict, and prints the merged table in file order. On stderr it first names what was swept (`mutate: sweep of <sha> with <mutant file> (sha256 <digest>)`), then the counts, among them the KILLED mutants whose killer is not one of their `expect` rows (`k killed by another row (expected=no)`).

**Why:** the merge takes under a second and runs no suite, so it costs the local machine nothing. A KILLED with `expected=no` is reported but does not make the sweep INCOMPLETE or the exit code non-zero: some selected row failed on the mutant while the control on the same runner was green, so it is a kill; whether it is the kill the mutant aims at (or a check that fires earlier, or a flake) the reader checks in the mutant's log, and failing the merge on it would turn a complete sweep into a re-run that cannot change a verdict. **Weak point:** the run page shows 20 shard tables, not one. **Rejected:** a merge job in the workflow, which needs `actions/download-artifact` outside the job `lighthouse` of `lighthouse.yml`, a guard exception against ADR-0003 part 2.

### 8. Budgets, the shard deadline and the job cap

Per mutant the runner waits B = 2 × T_control + 220 s, T_control the measured time of the shard's control for that suite set. A shard starts a mutant only if elapsed + B ≤ D, the shard deadline, and marks the rest NOT-RUN; so the runner ends cleanly before the job cap, and `timeout-minutes` only ever fires on a hang of the runner itself. The cap follows the method of ADR-0003 part 5: the factor times the slowest green shard job, rounded up to a 5-minute step as in ADR-0004's bucket rule. D = cap − 60 s. Derivations: Numbers.

**Why:** the budget scales with what the same runner just measured, so a slow runner gets longer budgets instead of false TIMEOUTs. **Rejected:** a fixed per-mutant timeout (a browser suite takes 450 s, a static one 120 s); no deadline (the job cap would cut a shard mid-mutant, and its artifact would lose every row).

### 9. Process: sweep branches

1. `git switch -c sweep/<pr>-<impl|qa>-r<round> <PR head sha>`, add `tests/mutants/<pr>-<impl|qa>-r<round>.jsonl`, scrub the staged diff, commit, push.
2. `gh workflow run mutation-sweep.yml -R Replikanti/interviewscam-site --ref <branch> -f mutants=<path>`.
3. Find the run whose head is the pushed commit (`gh run list --workflow mutation-sweep.yml --branch <branch> --event workflow_dispatch --json databaseId,headSha`) and poll `gh run view <id> --json status,conclusion`.
4. `gh run download <id> -D <dir>`, then `python3 -I -B tools/mutate.py merge <dir>`.
5. Delete the sweep branch once the run URL is in the PR or QA comment. Sweep branches are never merged.

QA branches from the PR head on its own, with its own mutant file, so its sweep is independent of the implementer's. The acceptance of the second PR: a census with one mutant per suite (a one-word edit of a prose line in `README.md`, every mutant SURVIVED with every control green, and the union of the control rows equal to the rows of that PR's `check` log), at least 100 browser mutants of `assets/js/search.js` on `reflow-search` and about 100 static mutants of render rule 17 on `render-report`, the two sets each run twice on the same ref with equal `id`, verdict and killer columns.

**Why:** a branch per sweep ties the run to one commit and one reviewed file, and two agents never share one. **Rejected:** sweeping on the PR branch itself (a mutant file in the PR diff, and every sweep push would re-run `check`).

## Consequences

- Agents trigger sweeps and read results; they never run one locally (part 1). The SDLC routing entry for this repo and the implementer and QA briefs say so from the second PR of Replikanti/interviewscam#40.
- A new block of self-test rows needs a `selftest_wants` guard with the suite it prints; without one, every `--only` run that does not select it fails with `row outside --only`. Renaming a row prefix renames its suite and changes every mutant file that names it (CLAUDE.md, Load-bearing names).
- `mutation-sweep.yml` is on `main` as a stub from the first PR. A run started on `main` before the second PR merges fails within seconds and changes nothing.
- Sweep branches and mutant files are public: every push passes the public scrub, and they hold only code edits, never records.
- A new runner image or Chrome version can move T; the controls absorb it per shard, and the double runs of the acceptance catch flips.
