# ADR-0009: Link preview metadata and cards

## Status

Accepted, 2026-11-24 (operator, Replikanti/interviewscam#44, STOP 1: the SPEC §6 paragraph and the §5 pointer as written, report cards with the D6 state sentence, campaign cards with type, name, dates and brand; after review run 1 of the first PR, decision 5: a report's text card starts with its D6 state chip, and the SPEC §6 sentence on the description says so). The plan splits the work into three PRs. Parts 1 to 3 are the text metadata of the first PR; parts 4 to 6 (the site card: generator, font and drawable set, layout and pixel check) came with the second PR; parts 7 and 8 (the record cards, their fallback and their checks) came with the third, which also closed the second PR's recorded list (the layout pins in part 5, the ink check in part 6, the card address that follows the font bytes in part 4, the fixture copies in part 8) and the first PR's known limit C4 (part 3), each with its Numbers.

## Context

- **A pasted link shows no card today.** Candidates share a report link in chat apps and on social networks, where the link shows only as a bare URL, because no page carries Open Graph or Twitter card metadata. The page's own `<title>` and meta description already state the record's name and summary, but card scrapers read their own keys first.
- **Card scrapers read the head only, with their own keys.** Open Graph names its keys with `<meta property>` (`og:title`, `og:description`, `og:url`, `og:type`, `og:site_name`); Twitter cards name theirs with `<meta name>` (`twitter:card`, `twitter:title`, `twitter:description`). A card travels without the page it came from, so its text carries the D6 state, the D7 label and the D10 label on its own, and an app that shows only the text (no image) still shows all three.
- **`property` is an RDFa attribute, which ADR-0004 part 8 banned outright.** Render rule 8 refused every `property`, and its comment stated that the base layout had no Open Graph `<meta property>`, so no exception existed.
- **No check read `<meta content>` as a link.** lychee 0.24.2 does not extract URLs from `<meta content>` (`lychee-lib/src/extract/html/html5gum.rs`, `extract_urls_from_elem_attr`), so a broken or foreign `og:url` would pass the link check.
- **The pinned Nu Html Checker accepts the tags.** `html_check` runs the image's `vnu` CLI without `--schema`, which then validates against `html5-all.rnc` ("HTML + SVG + MathML + RDFa", validator/validator `resources/presets.txt`); `schema/html5/rdfa.rnc` defines `meta.property.elem` in the head, and `schema/html5/meta.rnc` takes any non-empty `name`. `tests/fixtures/html/pass-preview-meta/`, committed alone first, proved it on the pinned image in CI before any template printed a tag.

## Decision

### 1. The tag set and the source of each value

`layouts/_partials/preview-meta.html`, called from `baseof.html` right after the canonical link and only where the canonical link is (every page but the 404), prints, in this order: `og:type` = `website`, `og:site_name` = the site title, `og:title`, `og:description`, `og:url` = the page's permalink, `twitter:card` = `summary`, `twitter:title`, `twitter:description`; the Open Graph keys as `<meta property>`, the Twitter keys as `<meta name>`, each with `content`.

- **Title:** Home `home.title`; the `reports` and `campaigns` section pages their fixed title (`record-title.html`); a record page the `<title>` form (`record-title.html` with `head`: the label-first form of a visible persona, the hidden title of a hidden one); every other page its `.Title`. So the card title is always the page `<title>` without " · interviewscam.com".
- **Description:** on a report page `preview.report_description` over the report's D6 state chip (`state.<state>.chip`), its D7 label (`report-label.html`) and its summary, so "Name abused. Reported once, evidence reviewed on 2026-10-30. …"; on a campaign page `preview.description` over `preview.campaign_fact` (its first and last seen dates) and its summary; every other page its meta description (`.Description`, or `site.description`).
- The two `twitter:` text values are the `og:` ones, so both scrapers show the same card. The values reach the attributes as returned partial values, never as printed partial output.

**Why:** the card is the page as a link. Reusing the `<title>` keeps the D10 label in front of a persona name where a card cuts a long title, as a search result does (ADR-0004 part 4). A report's summary alone states neither its D6 state nor a D7 fact, and a card travels without the page's chip and label, so both come first: the chip first, because a "Name abused" card must say before anything else that the name belongs to someone else, and an app that cuts the text keeps the start (review run 1 finding 1: `og:title` "Example Abused Company, a name used in fake job interviews" with a label-only description read like a report against the company). This PR's card has no image (`twitter:card` = `summary`), and apps that show only text never show the image of the later parts, so the text cannot leave the state to the image. A campaign has no state and no D7 label, and its dates are the facts its page states. `og:type` = `website` describes a page, never a person or an organisation (D6). `summary` is the card type without an image; the second PR changes it with the image. No tags on the 404: it answers for every missing URL, as it has no canonical link (ADR-0003 part 3).

**Rejected:** the summary alone as the record description (a card then states no D6 state and no D7 fact); the D7 label alone before the summary (the first version of this PR: no D6 state in the text, see Why); the state sentence instead of the chip (two sentences before the summary, so an app that cuts the text loses the summary first; the chip is the state's own short form, and the image of the later parts carries the sentence); `og:type` = `article` or `profile` (a claim about the content's kind, `profile` about a person); `twitter:site` and `twitter:creator` (an account claim the site does not make); `og:locale` (one language, the default); per-template blocks instead of one partial (four copies of the same rules).

### 2. One closed RDFa exception in render rule 8

`property` passes rule 8 only on a `<meta>` that is a direct child of the `<head>` of the root `<html>` (not of an `<html>` nested in the body), carries exactly `property` and `content`, and whose `property` is one of the Open Graph keys of part 1 (`PREVIEW_PROPERTIES`, compared as written). Every other use of the six RDFa attributes (`property` on any other element, in the body, with another key, with another attribute such as `lang`, `prefix` on `<html>`) stays a finding, and so does a `rel` CURIE. Render rule 20, the closed markup vocabulary (Replikanti/interviewscam#51, ADR-0004 part 14), lists `property` on no element; it admits the attribute on exactly the `<meta>` this part admits (`preview_property`, one function for both rules) and nowhere else.

**Why:** Open Graph needs `property`, and the only RDFa a parser can build from these tags is a description of the page as a link, never of a record's subject, so it is no structured data in the sense of SPEC §5 and ADR-0004 part 8. Each condition closes a route back to general RDFa: the place (an RDFa processor reads `property` anywhere), the attribute set (`about`, `resource`, `typeof` or `lang` change the subject or the literal) and the closed key list.

**Rejected:** lifting the ban on `property` (any RDFa statement about any subject); an exception by prefix `og:` (`og:see_also`, `og:audio` and keys of other vocabularies such as `article:author` would follow); Twitter keys as `property` (Twitter documents `name`).

### 3. The checks

- **Site rule (o)** (`preview_problems`, on every HTML page of both builds): (o1) every page but `404.html` holds exactly one `<meta>` per key, matched on the exact attribute value, and `404.html` none; a `<meta>` whose `property`, `name` or `itemprop`, folded (`guard_fold`, ASCII whitespace stripped), starts with `og:` or `twitter:` without being a key on its own attribute is a finding; (o2) the fixed values; (o3) `og:url` is the page's canonical URL as a whole string; (o4) each `twitter:` text value equals its `og:` twin as a whole string; (o5) `og:title` is the `<title>` with exactly one trailing " · interviewscam.com" removed, and `og:site_name` is `interviewscam.com`; (o6) on every page that is not a record's own page, `og:description` equals the meta description, both whitespace-collapsed; (o7) no text value gives an R11 or R12 finding (a live dotted name, IPv4, `www.`, an email on a live host; only the site's own host is exempt) or, in any reading of `rendered_variants`, holds a live URL, a protocol-relative `//host`, or an RFC 3986 scheme token followed by a non-space: a run `ALPHA *( ALPHA / DIGIT / "+" / "-" / "." )` that starts the value or follows a character that is no ASCII letter or digit (so a run starts after `+`, `-` or `.` too: "-tel:", ".sms:"), then `:`, in any case, other than the defanged `hxxp` and `hxxps` and a time-zone offset of prose (`PREVIEW_TZ_OFFSET`, fix round 3: exactly `UTC` or `GMT`, then `+` or `-`, one or two digits, `:` and exactly two digits, followed by the end, whitespace, `)`, `,`, `.` or `;`, so "15:00 (UTC+01:00)", "GMT+1:00" and "UTC-05:30" pass; a summary may give an interview time this way, and the one shape held open carries no host or path a link could open, while `utc+01:x`, `UTC01:00`, `UTC+100:00` and `est+05:00` stay findings); a run may also start right after a digit (third PR, the first PR's known limit C4: "1tel:+1" is a scheme to a linkifier that starts a link at any non-letter), with one more exception, the ISO 8601 time of prose (`PREVIEW_ISO_TIME`: after a digit, exactly `T` and two hour digits, `:`, two minute digits, optional `:` and two second digits with an optional fraction, an optional `Z` or `+`/`-` offset of two digits with optional `:` and two digits (a sign and a digit that no offset took fails), then no digit, no `:` before a non-space and no `/` unless a digit or a duration `P` or `PT` and a digit follows (fix round 2 of the third PR, review run 2 finding 1, and its post-cap fix, review run 3 finding 1). Why that is enough: the exemption covers only the time's own run, `T` and two digits, a scheme no handler opens, and the scan for scheme runs starts again right after its `:`, so any scheme later in the text is a run of its own and a finding, glued or not (`10:30tel:+1`, `10:30UTCtel:x`, `10:30:00Ztel:x`, `10:30am:x`). It is not that a URI token ends after the time: under RFC 3986 a letter and `? # @ & = ~ _ ! * ' ( ) [ ] % $` all continue one, so `2026-11-02T10:30?x=1` is one token with the scheme `t10` to a generic parser, harmless for the same reason. The three refusals bound the shape (a digit would lengthen the minutes, seconds or offset, a `:` or `/` before more text reads as a further segment); they are not the D8 argument. So prose punctuation passes (`!`, `?`, `: `, quotes, `]`, `»`, a dash, an en-dash or hyphen range, `/P1D`, a U+2212 offset), and so do ASCII letters glued to the time, a zone or clock suffix (`10:30UTC`, `10:30:00UTC`, `10:30CET`, `10:30h`, `10:30am`; rejected: refusing them, as fix round 2 did, failed such prose with an instruction to add a space after the colon, and added no D8 protection: a brute force over 1- and 2-letter glue and every BMP separator between three time forms and ten schemes found no passing scheme either way); the optional tail is one atomic group, so once it has taken a fraction the reading without it is not tried (`02T10:30:00.5:x` fails), fix round 1 of the third PR), so "2026-11-02T10:30", "2026-11-02T10:30Z", "2026-11-02T10:30:00Z", `"2026-11-02T10:30Z"!` and "2026-11-02T10:30UTC" pass while `1tel:+1`, `2h323:x`, `02T10:x`, `02T1:30`, `02T10:3`, `02T10:300`, `02X10:30`, `02T10:30+1`, `02T10:30Z9`, `02T10:30:00.5:x`, `02T10:30am:x`, `1t10:30:evil`, `1t10:30/evil`, `02T10:30/Px` and `02T10:30tel:+1` fail; and `og:url` is the site origin, `/`, a path and nothing else; (o8) the scraper's view: every `<meta`, in any case, in the raw page starts a `<meta>` element the parser read at the same source position (so a tag in a comment, an attribute value or a script is a finding, and a tag only the parser reads cannot offset one only a scraper reads, as counting did); each of the eight preview metas is exactly `<meta property="KEY" content="…">` or `<meta name=KEY content="…">` as the template and the pinned minifier write it (the key attribute first, then `content`, nothing else; the key quoted or bare, `content` in double quotes, or in single quotes when the value holds a double quote, because the minifier then switches); and no element on the page repeats an attribute name. Records rule R20 (`raw_meta_problems`, on every record and `_index.md`) refuses `<meta` in any case (`PREVIEW_RAW_META`) in each front-matter string that reaches a preview attribute (`PREVIEW_META_FIELDS`, read from `preview-meta.html` and the partials it calls: a record's `params.name`, unless a hidden persona's, and `params.summary`, and an `_index.md`'s `description`), because the pinned minifier writes a value's `<` raw into the preview attributes, so the record stage names the file, the field and its preview keys before (o8) fails the built page; as written, because `&lt;meta` stays escaped on the page. Only those fields, not every string (fix round 3, review run 3 finding A): every other string renders as element text, where the build escapes the `<`, and refusing it there refused legitimate records (a "Name <address>" sender line in `evidence`, a source title quoted as the source wrote it); (o8) stays the backstop if a template moves another field into the head, and `records-meta/coverage` fails when a preview partial reads a field that is neither pinned nor listed with the reason it reaches no preview. With `--no-built-pins` (hand-made fixtures) only the look-alikes of (o1), (o7) and (o8) run. Rule (m) pins the eight children in place in the exact head.
- **Render rule 4** gains one own-page exemption: on a visible persona's own page the content of the single `og:title` and the single `twitter:title` meta, when it reads exactly the label-first `<title>` form. Every other copy of the form, on that page or any other, stays in the scan.
- **Render rule 8**: part 2.
- **Render rule 21** (`preview_record_problems`, on a record's own page with the real-build pins on, as rule 17; rule 20 is the closed markup vocabulary of Replikanti/interviewscam#51, ADR-0004 part 14, which admits `property` only where part 2 does): `og:title` is the record's `<title>` form; a report's `og:description` is `PREVIEW_REPORT_DESCRIPTION` over its state chip, which equals the page's own state chip, its D7 label, which equals the page's `record-label` element, and its summary; a campaign's is `PREVIEW_DESCRIPTION` over `PREVIEW_CAMPAIGN_FACT` (`first_seen` and `last_seen`, which equal the page's First seen and Last seen facts) and its summary. The three label strings are pinned a second time in `sitecheck.py`.
- **`literals`**: `property` joins `LITERALS_PLAIN_ATTRS` (its value is a key, never shown); a `property` meta on `LITERALS_META_PLAIN_PROPERTIES` (`og:type`, `og:url`, exactly as written) or a `name` meta on `LITERALS_META_PLAIN_NAMES` (now with `twitter:card`), with no other of `name`, `property`, `itemprop` and `http-equiv`, has content that is no text: one lowercase token or an action; every other `property` meta keeps visible content (L2 and the print sinks).

**Why:** a card is copy that travels without its page, so its text is held to the page it describes (o2 to o6, rule 21) and to D8 (o7), and no key can reach a scraper without a check reading it (o1, o8). Rule 21 needs the records, so it is a render rule; rule (o) needs only the built page, so it runs on every page. Rule 21 runs only with the real-build pins because the self-test's hand-made render pages predate the metadata, and both builds always run it (`wiring/render-report-pins`). The exemption of rule 4 is exactly the one the `<title>` already has, for the same reason. Rule (o5) compares whitespace-collapsed text because the `<title>` text the parser gives is collapsed. The scheme token of (o7) needs a non-space after the colon and a token start, so prose keeps its colons ("Note: x", "10:30", "2026-11-02T10:30"); a colon glued to a word ("Re:x", a defanged host with a port) fails closed and is written with a space or without the port. Why no count of letters closes C4: the first PR let a run start only after a non-alphanumeric character, so the `T10` of "2026-11-02T10:30" was no token; a rule "a run after a digit needs two letters" would pass that time and still miss five schemes of the IANA registry that hold fewer than two letters (`h323`, `i0`, `p1`, `w3`, `z39.50`; 457 schemes, `uri-schemes-1.csv` read 2026-11-25), so the third PR starts a run after a digit too and holds the one prose shape open by its whole form, as `PREVIEW_TZ_OFFSET` does: the time carries no host or path a link could open. The exact start tags of (o8) were read from a build with the pinned Hugo's minifier: it drops the quotes of `name=` and keeps those of `property=` and `content=`, and writes `content='…'` when the value holds more double than single quotes.

**Rejected:** a key allowlist without look-alikes (a scraper may fold case or trim); checking the values only in render (the section and static pages have no record); counting the tags a scraper regex reads against the tags the parser reads (the first version of this PR: one content-first tag that the regex misses and one decoy in an attribute value that only the regex reads cancel out, review run 1 finding 2); a closed list of schemes for (o7) (the first version: `mailto:` and the file schemes; `tg:`, `tel:`, `sms:`, `skype:`, `intent:`, `magnet:` and `ipfs:` passed, and a messaging app may linkify its own scheme, review run 1 finding 3).

### 4. The generator: Hugo draws the card at build time

`layouts/_partials/preview-image.html` draws the card with the pinned Hugo 0.169.0: one `images.Filter` call over one slice of filters on the 1 x 1 base image `assets/og/base.png`: `images.Padding` grows it to the canvas in the ground colour, a second `images.Padding` with negative sides crops the base pixel away, a third adds the bar at the left edge in the primary colour, and one `images.Text` per line draws the text with a bundled font. Hugo publishes the result as `/og/base_hu_<hash>.png`; the hash covers the filters (texts, positions, colours, the font's resource path) and the base image's bytes, so a wording change gives the card a new address. The fonts reach `images.Text` through `resources.Fingerprint` (third PR, the second PR's recorded item B3): their resource path then holds the SHA-256 of their bytes, so a card drawn with other font bytes gets another address too, and a preview service that keyed its copy by the address fetches the new card. Measured with the pinned Hugo on 2026-11-25: a new base image changed the name before the change, a swapped font did not (the same name, other bytes), and with the fingerprint it did; the font is still never published (site rule (o12)). `[caches.images] maxAge = 0` in `hugo.toml` turns Hugo's file cache of processed images off: `resources/images/text.go` keys a drawn image by the font's resource path, not its bytes, and a build with the default (never expire) reused the old card under the same name after the font file was swapped (measured with the pinned Hugo, 2026-11-25: the same name, the old bytes); with `maxAge = 0` the same swap redrew it. The guard pins the key and reads it in the effective config (`hugo config` prints it as `"0s"`).

How Hugo draws (`text.go` at v0.169.0, `golang.org/x/image` v0.47.0): `font.Drawer` with `opentype.NewFace` at 72 DPI and `HintingNone`, the baseline at `y + Ceil(ascent)`, every advance rounded to 1/64 px, and its own wrap: `strings.Fields` splits the text, and a word goes to a new line when the rounded width of the line so far (with a trailing space) plus the word's reaches `(image width - 20) - x`; a first word that is too wide gets an empty line before it. x/image applies GPOS pair kerning: `sfnt.Font.Kern` reads the `kern` feature lookups of the `latn` (else `DFLT`) script, pair-adjustment subtables (lookup type 2, or 9 wrapping 2) whose value formats are exactly X_ADVANCE of the first glyph. (The font has no `kern` table, but x/image reads GPOS too, as its source and a measurement with it show, so part 5's tables carry a kerning bound.) So the template breaks the lines itself (part 6), each line stays under Hugo's own wrap width (Numbers), and Hugo never re-wraps one.

Determinism: the same Hugo, font bytes, base image and text give the same pixels, and Go's PNG encoder writes only IHDR, IDAT and IEND, so the bytes match too (`preview-image/deterministic` builds a site with the real partials twice). The file name does not depend on the checkout's path (the production build, the fixture build and two temporary builds gave the same name). `security.exec` stays `none`: no external program draws anything.

**Why:** the card text comes from the same template data as the page (one implementation), the toolchain gains no binary, and every build, the metered records-mode build included, draws the cards in the same Hugo run that builds the pages.

**Rejected:** a Rust generator (a second implementation of the record-to-card text that can drift from the page, a cargo build or another pinned binary in the records-mode build, and a step between two Hugo runs; Rust lost on those, not on the language); Python with Pillow (not the standard library, a pip supply chain in CI, against ADR-0002); ImageMagick or rsvg from the runner image (unpinned, they differ between runner images); SVG cards (the large chat and social apps take raster `og:image` only; see Numbers for the assumption); Hugo's own wrapping (it breaks only at spaces, puts an empty line before a too-wide first word, and its width model is not readable by any check); keeping the image cache (it reuses a card drawn with a replaced font, above).

### 5. The font, the drawable characters and the metrics table

The card draws with Noto Sans v2.015, unhinted static Regular and Bold, from `notofonts/notofonts.github.io` commit `28b15b4b43b7bed62b5cf6e6b0b5ff5846270535` (`fonts/NotoSans/unhinted/ttf/`), stored as `assets/fonts/noto-sans-regular.ttf` and `assets/fonts/noto-sans-bold.ttf` (lower-case names, because `literals` reads a resource name in a template as a literal, which must be one lower-case token), with its SIL Open Font License 1.1 text in `docs/licenses/NotoSans-OFL.txt` (`OFL.txt` of `notofonts/latin-greek-cyrillic` at commit `ffaec0a756877220dbf718ce08b8479a0be82479`; under `docs/`, because a text file under `assets/` fails `literals` L1). The OFL allows bundling and redistribution with the licence text alongside. D9 holds: the text is rasterised at build time, the font is never published (site rule (o12)), and a card needs no request at view time.

The drawable characters are the code points the font maps to a glyph with a non-zero advance in Basic Latin U+0020 to U+007E, Latin-1 U+00A0 to U+00FF, Latin Extended-A and -B U+0100 to U+024F, Greek U+0370 to U+03FF, Cyrillic U+0400 to U+04FF, Latin Extended Additional U+1E00 to U+1EFF and General Punctuation U+2010 to U+2044, minus every default-ignorable code point (`INVISIBLE`), every space Go's `strings.Fields` splits on except U+0020 (`PARSER_ONLY_SPACE`, U+00A0 among them: Hugo would redraw it as U+0020 at another width), C0 and C1, and the bidi classes R and AL of the vendored `DerivedBidiClass.txt` (x/image draws in logical order and does not shape). Every input is a pinned file, so the set is the same on every runner.

`sitecheck preview-metrics` reads the two fonts with a standard-library reader (`font_metrics`: the sfnt directory, `head`, `hhea`, `maxp`, `hmtx`, `cmap` formats 4 and 12 of every Unicode subtable, which must agree on the blocks above, `OS/2`'s typo metrics, which must equal `hhea`'s while USE_TYPO_METRICS is set, the `loca`/`glyf` bounding boxes, and `GPOS`; a `kern` table, CFF outlines or any other shape is a finding naming the file, never a traceback) and prints the generated part of `data/preview.toml`: per face `units_per_em`, `ascender`, `descender`, `line_gap` and `ink_slack` (the largest overhang of a drawable glyph's outline past its advance box or past the ascender and descender, at the largest size a card draws, plus 2 px), the advance of every drawable character, and the kerning bound: for every pair of drawable characters the largest positive value any GPOS pair-adjustment subtable of any lookup gives it. x/image takes the first subtable of a kern lookup that covers the pair, so the largest positive value over all subtables is an upper bound of what it applies whatever the lookup order; a negative kern only narrows a line, so the bound leaves it out. Keys are TOML basic strings, printable ASCII as written and everything else as `\uXXXX`, so no editor's normalisation can merge two keys; Hugo keeps data keys as written (`preview-wrap/case-distinct` measures `A` and `a` apart on a real build).

The guard holds it all (`guard_preview_pins`): the four files of `PREVIEW_ASSET_SHA256` (base image, two fonts, licence) are regular files with their SHA-256; `assets/og/` and `assets/fonts/` hold nothing else; no other font file (`.ttf`, `.otf`, `.ttc`, `.woff`, `.woff2`, folded) lies under `assets/` or `static/`; `data/` holds exactly `labels.toml`, `preview.toml` and `tokens.toml` (Hugo merges every file under `data/` into `hugo.Data` by its path, so `data/preview.yaml` or `data/preview/x.toml` would merge into the card metrics); the base image is exactly 1 x 1, 8-bit RGB; the part of `data/preview.toml` from the line `PREVIEW_METRICS_MARK` on is byte for byte the output of `preview-metrics`; the layout tables hold exactly their keys, each value exactly the one pinned a second time in `PREVIEW_LAYOUT` (third PR, the second PR's recorded item B1: `description_size = 1` passed the guard, the build and the pixel check while the alt still named the description), the canvas is 1200 x 630, the margin covers the X crop and the bar plus the ink slack, and no size exceeds the size the slack is measured at. A pin, not a floor: a floor derived from the layout (36 px reads as about 11 CSS px on a phone, Numbers) would still let a size move between the floor and the slack size, and every size change changes what a card can hold, which part 7's fit and the pixel check then have to meet; with the pins a size change is a `tools/` change with the safety-net review. A root that holds none of the card files (another rule's guard fixture) is left out, because the real templates fail the build without `data/preview.toml`, a font or the base image (measured: `sub` of nil, `invalid text font source: <nil>`). `literals` L6 passes exactly the pinned files under `assets/` while their bytes match, and so does the colour scan of `tokens` for the two fonts (a font holds no CSS colour; any other file that is neither UTF-8 nor a raster image still fails closed).

**Why:** a card is copy drawn as pixels, which no text check reads, so what can draw it (the font, the base image, the numbers) is pinned, and the model the wrap uses is derived from the pinned fonts by a check, never typed by hand. The kerning bound keeps "a line fits" true for the pixels Hugo draws, not only for the model.

**Rejected:** Hugo's embedded Go Regular (one weight, WGL4 only, its tables inside the Hugo binary, where no check reads coverage or widths); DejaVu Sans (adds Hebrew and Arabic, which x/image can neither order nor shape, larger); Inter (no wider Latin coverage for this use, larger files); a variable font (x/image draws only its default instance, so no Bold); the exact x/image kerning (first matching subtable) in the table (a replica of its lookup order, for at most a few units per pair; the bound over-counts 390 pairs per face, Numbers); advances alone (the plan's first model: a line of positive pairs could pass Hugo's wrap width, Numbers).

### 6. The site card, the wrap and the checks

Every page but the 404 links one site card (record cards come with part 7): the brand (`header.brand` and `header.brand_tld`, Bold, 72 px, the text colour), then the site description (`site.description`, Regular, 40 px, the muted colour), on the ground colour with a bar in the primary colour at the left edge; all three pairs on ground are listed `[[pair]]`s of `data/tokens.toml`. Lines start at the margin; a block's lines follow at its line pitch, the font's own line height `ceil((ascender - descender + lineGap) x size / unitsPerEm)`, and blocks are a gap apart. A card whose blocks run below the content box fails the build (`errorf`). `preview-meta.html` adds, after `og:url`, `og:image` (the card's permalink), `og:image:type` `image/png`, `og:image:width` and `og:image:height` (the image's own size) and `og:image:alt`, and after `twitter:description` `twitter:image` and `twitter:image:alt`; `twitter:card` becomes `summary_large_image`. The alt is `preview.alt_site` over every drawn block in drawing order, so it holds the image's whole text: "interviewscam.com: A community registry of fake job-interview scams that target developers."

`layouts/_partials/preview-wrap.html` breaks a block into lines: greedy at U+0020 (runs collapse, empty words drop), never inside a word, a line's width the sum of its advances plus every positive kern of a neighbouring pair, in font units, fitting when `units x size <= width x unitsPerEm` (the bound inclusive). It returns `false` when a character has no advance entry (not drawable) or a word is wider than the line (from the third PR's fix round 1, part 7). Two `errorf` guards turn a wrapping bug into a failed build instead of a card that lost text: the lines joined back with U+0020 equal the space-collapsed text, and every line measured again on its own fits. `sitecheck preview_wrap` is its replica in Python; `preview-wrap/<row>` builds a site with the real partial and data and needs the template and the replica to give each row's expected lines (the empty text, one character, a line and a word exactly the width and one unit over, a word over twice the width and a word after a full line (`false` from the third PR), two spaces, edge spaces, U+00A0, U+0301 and an emoji (`false`), `·`, a positive kern at its exact width and one unit under (`false`), the D10 label at each name size of part 7, and the two site card blocks).

Site rule (o) gains the image branches: (o9) `og:image` and `twitter:image` are the same whole string, `https://interviewscam.com/og/<name>.png` with a name of `a-z`, `0-9`, `_` and `-` (`PREVIEW_IMAGE_URL`: no other host, scheme, userinfo, port, case, dot segment, escape, query, fragment, directory or type), naming a regular file of the built tree; (o10) that file is a PNG (`png_problems`: the signature, IHDR first, 1200 x 630, bit depth 8, colour type 2 or 6, no interlace, then only IDAT chunks and an empty IEND, every CRC right, nothing after IEND, because an ancillary chunk such as tEXt, zTXt, iTXt or eXIf carries text no check reads), and `og:image:type`, `:width` and `:height` are exactly `image/png`, `1200` and `630`; (o11) `og:image:alt` equals `twitter:image:alt`, and both are text keys for (o7); (o12) every file under the built `og/` is some page's `og:image`, and no font file is anywhere in the built tree; (o13) with the built pins, every page that is not a record's own page has Home's `og:image`, and its alt is the site card's (`PREVIEW_ALT_SITE`, the label's text pinned a second time). `site --preview-pixels` decodes every card (`png_pixels`: zlib and the five PNG filter types, standard library only) and needs every pixel outside the content box grown by the ink slack, right of the bar, to be the ground colour and every pixel of the bar the primary colour; a finding names the image, the count and the first pixel. From the third PR (the second PR's recorded item B2: a description drawn in the ground colour passed) it also reads the text the alt names (`preview_ink_problems`): for each page that links the card, `preview_card` (part 7) gives the lines it draws, and each line's box (from the margin to its measured width plus 2 px, one pitch high) must hold at least one pixel of exactly its block's colour, while every pixel outside every line's box grown by the ink slack is the ground colour, so a line in the ground colour, in another token's colour, left out, moved or not in the alt is a finding. `check.sh` passes it on the fixture build only (`wiring/site-preview-pixels`): its cost grows with the records, on the private repo's metered minutes, and the fixture build draws the same template, whose `errorf` guards hold every build.

`literals`: the two partials are the only callers of `split` (with the label partials), `mul`, `sub`, `div` and `float` (with `tokens.css`), `math.Ceil` and the three `images.*` functions (`LITERALS_FILE_FUNCTIONS`; no other `images.*` function, `images.QR` among them, is on `LITERALS_FUNCTIONS`); `resources.Get` also runs in `preview-image.html`, with the three new names on `LITERALS_RESOURCE_KEYS`, and from the third PR `resources.Fingerprint` too (the fonts' SHA-256 in the card's address, part 4; the card partial's dict keys gain `blocks`, `lines` and `pitch`, and the literal `0`, the site card's name size, is a collection value there); `hugo.Data.preview` is read only in the two partials (`LITERALS_PREVIEW_DATA_READERS`); their dict keys and the face names are file-scoped (`LITERALS_FILE_DICT_KEYS`, `LITERALS_COLLECTION_VALUES`); the number literals `0` and `-1` pass only there (`LITERALS_FILE_NUMBERS`, a new passing set); `Width` and `Height` join `LITERALS_MEMBERS`; `og:image`, `og:image:type`, `og:image:width`, `og:image:height` (`LITERALS_META_PLAIN_PROPERTIES`) and `twitter:image` (`LITERALS_META_PLAIN_NAMES`) carry no text, while the two alts stay visible attributes; and the text operand of `images.Text` is a print sink of its own that takes only what a visible attribute takes, so a literal, a URL, a number or a word Hugo writes drawn into an image fails as it would in an `alt`.

**Why:** the card is held from both sides: what draws it (the template guards, the pinned font and model, the print sink of `images.Text`) and what it became (the PNG's form and its pixels), because no text check reads pixels. The alt carries the whole drawn text, so a screen reader and every text rule (o7) see what the image shows.

**Rejected:** a site card with more text (a tagline per page: an image per static page is out of scope); text centred in the card (the record cards of part 7 fill the box from the top, and one alignment keeps the pixel model simple); the pixel check on every build (part 6 above); comparing the card with a committed reference PNG (it would pin Hugo's anti-aliasing, so any Hugo upgrade fails it without a defect, while the band check pins what matters, nothing drawn outside the box).

### 7. The record cards

A report's own page links its report card, drawn by the same `preview-image.html` from the same template data as the page, top to bottom: the chip line, `preview.chip_line` over the D6 state chip and the name type (`state.<state>.chip`, `name_type.<type>`, as the type line under the h1 shows them; Bold, 36 px, primary); the name as `record-name.html` gives it in plain text (a visible persona with its D10 label after the name, a hidden one as `persona.hidden_name`; Bold, the name size, text); the D6 state sentence (`state.<state>.sentence`, STOP 1 decision 2; Regular, 36 px, text); the D7 label (`report-label.html`; Regular, 36 px, muted); and the brand (Bold, 36 px, primary). A campaign's own page links its campaign card: `a_z.campaign_type`, the name, `preview.campaign_fact` over its first and last seen dates (Regular, 36 px, text) and the brand (STOP 1 decision 3). The name size is the first of `[record] name_sizes` (72, 60, 48, 40) at which every block has lines, no word is wider than a line, and the blocks end inside the content box; the other blocks keep `[record] text_size`. The alt is `preview.alt_report` or `preview.alt_campaign` over every drawn block in drawing order (`"<chip line>. <name>. <sentence> <D7 label>. interviewscam.com"`, `"Campaign family: <name>. First seen …, last seen …. interviewscam.com"`), so the alt is the image's whole text, as on the site card. The partial returns the drawn lines and the name size with the image and the alt.

`sitecheck`'s `preview_card` is the replica of the partial (the same candidates, wrap, pitch and fit over the parsed `data/preview.toml`, with the labels pinned a second time: `PREVIEW_CHIP_LINE`, `PREVIEW_ALT_REPORT`, `PREVIEW_ALT_CAMPAIGN`, `PREVIEW_BRAND`, `PREVIEW_SITE_DESCRIPTION`), and `preview-fit/<row>` builds a site with the real partials and one record per row and needs the template and the replica to draw the same lines with the same alt (the four sizes, a fit at exactly the content height and one pixel over it, a name of four lines at 40 px, a word too wide for a line at every size, a visible and a hidden persona, the four D7 branches, both states, a campaign, and the names the font cannot draw).

**Why:** the card travels without its page (part 1), so it states what the page's top states, in the page's words: the D6 state and its sentence (a "Name abused" card must say the name was used without the owner's involvement), the D7 label, and the name with its D10 label, never a bare persona name. The name is the only text whose length the site does not control, so only its size steps; 40 px is the last step above the 36 px text, so the name stays the largest text. The replica exists because render and the pixel check need to know what a page's card says without decoding text from pixels.

**Rejected:** the chip as a coloured shape (out of scope: a shape is no text, and the chip text alone carries the state); shrinking every block with the name (the facts would fall under the phone-feed floor of Numbers); cutting the name with an ellipsis (a cut name can read as another name, and a cut D10 label would lose the label; the site card is the fallback instead, part 8); breaking a word that is wider than a line between characters (the second PR's wrap; fix round 1 of the third PR, review run 1 finding 1: the break drops the word boundary from the image, so `Talentacquisitionrecruitmentpartnershipsexecutivesearch Group` and the same name with a space after `partne` drew one identical card at 60 px, the same file with two alts, which rule 21 fails on two valid records, and the card showed one name as two words; the site card is the fallback instead, part 8); a break mark (a hyphen or another glyph drawn at the break: it is text the name does not hold, which the alt and the replica would have to carry as well, and a hyphen at the break reads as a hyphenated name); a card per alias (one card per page).

### 8. The fallback and the checks

A record whose name has a character the font tables lack (`preview-wrap.html` gives `false`: a combining mark, a CJK or right-to-left letter, an emoji, a U+00A0 run, part 5), whose name holds a word wider than a line at every name size (`false` too, part 7), or that fits at no name size, links the site card with its alt, as every other page does; `og:title` and `og:description` still name the record in text. The site card is the last candidate and always fits; if it did not, the build fails. The fixture records hold the three cases: `example-accent-mark-studio` (U+0301 after `x`), a company name of 185 characters, four lines at 40 px, and `Talentacquisitionrecruitmentpartnershipsexecutivesearch Group`, whose first word fits no line (from fix round 1, with `Talentacquisitionrecruitmentpartne rshipsexecutivesearch Group`, which wraps at its space and draws its own card at 60 px; the 60-character single-token name of the reflow fixture also gets the site card now).

- **Render rule 21, card branch** (`preview_card_problems`, with the real-build pins, over the replica of each own record page; `data/preview.toml` of the checkout `sitecheck.py` belongs to, which every build reads): a record whose card fits links an image other than Home's and an `og:image:alt` equal to the replica's, whitespace collapsed (so the D6 chip and sentence, the D7 label, which rule 21 already ties to the page's `record-label`, and the name as it renders); a record whose card does not fit links Home's image with the site card's alt; and two pages link one image only when their alts are equal, so a page cannot link another record's card. Rule 4 reads the alt as it reads every attribute (a visible persona's name needs its label), rule 9 too (a hidden persona's name nowhere).
- **`--preview-pixels`** (part 6) reads every card against the lines the replica gives for each page that links it.
- **`site --preview-copies <dir>`** (`preview_copy_problems`; `check.sh` passes the fixtures directory on the fixture build only, `wiring/site-preview-copies`): every file under `tests/fixtures` in a directory `og/` with a built card's name (`<stem>_hu_<hash>.png`, `PREVIEW_BUILT_NAME`; the hand-made PNG cases name theirs `card.png`) equals byte for byte the card of that name in the fixture build, which draws the site card and every fixture record's card. Since the address covers the text, the base image and the fonts (part 4), a copy left over from an older card is a finding, and so is a copy whose bytes drifted (the second PR's recorded item B3).

**Why:** a record card is copy about a real company or person drawn as pixels, so what it says is held from three sides: the template's own guards, the replica that render compares with the page's text (D6, D7, D10 on the alt), and the pixels compared with the replica's lines (part 6). A fallback card says less but nothing wrong; a card that lost a character would draw another name. The ink check reads that each line is drawn in its colour inside its box and nothing outside the boxes, not which characters or at what size; a change of the drawing that keeps a pixel of each colour in each box still changes every card's address (the name covers the filters), so every committed copy goes stale, `--preview-copies` fails until they are copied again, and the new images enter the PR's diff, where a content PR's review looks at them.

**Rejected:** a check that reads the card's text back from the pixels (an OCR in the standard library is out of reach, and the replica gives the text exactly); drawing an undrawable character with a fallback font (a second font that nobody measured, part 5); comparing record cards with committed reference PNGs as the only check (part 6: it pins Hugo's anti-aliasing; the copies compared here are the fixture copies the self-test needs anyway, refreshed from the build).

## Numbers

Parts 1 to 3 have none: every value is a fixed string or derived from the page. Parts 4 to 6:

- **Canvas 1200 x 630 px.** Assumption from the consumers' card documentation, not re-read in this change (the pages render by script; check them in a browser before M6): Meta recommends 1.91:1 at 1200 x 630, and X's large card shows 2:1, cropping (630 - 600) / 2 = 15 px at the top and the bottom. At half the size the card looks blurred on 2x screens; another ratio gets cropped by one of them. Raster only: the same documentation lists PNG, JPEG, WEBP and GIF, not SVG.
- **Margin 56 px on every side, bar 16 px inside the left margin.** The margin must hold X's 15 px crop plus the ink slack (16 px): 31 px, and the bar plus the slack: 32 px; 56 leaves 24 px to spare for a wider drawable set. Content box x 56 to 1144 (1088 wide), y 56 to 574 (518 high). If the slack grew past 41 px (a wider drawable set), the guard fails until the margin grows by the excess.
- **Wrap width 1088 px against Hugo's 1124.** Hugo re-wraps a line when its rounded width reaches `(1200 - 20) - 56 = 1124` px; a template line is at most 1088 px by the bound (advances plus positive kerns), and Hugo's measure (advances plus its actual kerns, each part rounded up once) is at most that plus 2 px, so Hugo never re-wraps. Without the kerning bound a line of positive pairs could pass: the largest positive pair kern is 130 units in Regular (U+0129 U+0129) and 163 in Bold (U+0165 then `)`), 5.2 px and 6.5 px at 40 px.
- **Ink slack 16 px.** The largest overhang of a drawable glyph, measured by `preview-metrics`: 191 units (Regular) and 192 (Bold), both U+2044 FRACTION SLASH past its left side, 13.8 px at 72 px, rounded up to 14, plus 1 px for the anti-aliased edge and 1 px for Hugo's rounding (the baseline at `y + Ceil(ascent)` and every advance rounded to 1/64 px).
- **Sizes: brand 72 px, description 40 px.** A phone feed shows the card about 360 CSS px wide, 0.30 x, so 72 px reads as about 22 px and 40 px as about 12 px; 36 px (the record cards' text) reads as about 11 px, 32 px as 9.6 px. Measured: the brand is one line at 72 px, the description two at 40 px.
- **Line pitch** `ceil(1.362 x size)`, the font's own line height (ascender 1069 + |descender| 293 + lineGap 0 per 1000 units): 99 px at 72, 55 at 40 (and 50, 66 and 82 at 36, 48 and 60 for part 7), so lines never overlap. **Gap 24 px** between blocks, about half a 36 px pitch. The site card fills 99 + 24 + 2 x 55 = 233 px of the 518.
- **Drawable characters: 1,196 per face.** 1,213 mapped in the blocks, 1,201 with a non-zero advance, minus U+00AD (default-ignorable) and U+00A0, U+2028, U+2029 and U+202F (`PARSER_ONLY_SPACE`). **Kerning bound: 2,048 positive pairs (Regular), 2,058 (Bold).** Measured against x/image v0.47.0's own `Kern` over every drawable pair (2026-11-25): it applies a positive kern to 1,658 and 1,668 pairs, the bound covers each with a value at least as large (0 under-estimates) and over-counts 390 pairs per face (pairs a first subtable kerns by 0 or less). `data/preview.toml` holds 6,515 generated lines (111 KB); Hugo reads it once per build.
- **Fonts: 431,364 and 432,376 bytes** (SHA-256 `f3961a9c…` and `87cb2d84…`, `PREVIEW_ASSET_SHA256`), about 0.86 MB of the repo, never published. **Base image: 69 bytes.** **The site card: about 53 KB** (one per build).
- **Pixel check cost: about 1 s per card** (measured locally on the site card, decode and bands; the Paeth rows dominate), on the fixture build only: one card in this part, one per fixture record from part 7.
- **`maxAge = 0`:** part 4; any positive value can reuse a card drawn with a replaced font within that age.

Parts 7 and 8:

- **Record text 36 px, name sizes 72, 60, 48, 40 px** (`[record]`, pinned in `PREVIEW_LAYOUT`). 36 px reads as about 11 CSS px in a 360 px phone feed (0.30 x); 32 px would read as 9.6 px. 72 px is the brand's size and the largest the ink slack is measured at; each step is about 5/6 of the last; 40 px is the last step above the 36 px text. Pitches 50 (36 px), 99, 82, 66 and 55 px.

A campaign card leaves 518 - (3 x 50 + 3 x 24) = 296 px. ## Consequences

- Every page but the 404 grows by eight head children; rule (m)'s exact head, the head fixtures of the self-test and every real-build fixture copy carry them.
- A wording change of a title, a description, a state chip or the three `preview` labels changes the cards; the labels are pinned a second time in `sitecheck.py`, so such a change is a safety-net diff too.
- A card an app has already fetched keeps its old text until the app reads the page again. A removal or a hidden name therefore does not reach copies held by those apps (SPEC §6).
- The second PR replaced `twitter:card` = `summary` with `summary_large_image` and added the image keys; the Nu Html Checker fixture held them from the first PR.
- Every page carries fifteen head children of the preview; the real-build fixture copies carry them and the card file. A wording change of the brand or the site description changes the card, its address and `PREVIEW_ALT_SITE`.
- A font upgrade is a re-pin: new files, `PREVIEW_ASSET_SHA256`, the regenerated `data/preview.toml` (`preview-metrics`), and the self-test's expected wraps; the guard fails until all of them agree.
- An app that cached the old card keeps it until it reads the page again (SPEC §6); a new card text, base image or font gets a new image address (part 4).
