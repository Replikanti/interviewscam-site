## Decision

Plain HTML forms on `/report-a-scam/` and `/corrections/` POST (`multipart/form-data`, no JavaScript) to one first-party endpoint, `https://intake.interviewscam.com/submit`: a Cloudflare Worker on a Workers Custom Domain. The Worker validates the submission, rate-limits it through a Rate Limiting binding and a SQLite-backed Durable Object, both keyed by an HMAC of the client's IP prefix, and mails each accepted submission through a `send_email` binding fixed to the operator's verified address. It stores no submission and answers with `303` redirects to static result pages on `https://interviewscam.com`, so every word a reporter sees from the Worker stays under the existing `literals`, `render` and Lighthouse checks.

### 1. Intake path

Form, then the Worker at `https://intake.interviewscam.com/submit` (one path, `POST` only), then `send_email` with `destination_address`, then the operator's mailbox. No storage of submissions: no KV, R2 or D1, and no request body in any log. The Durable Object holds only rate-limit rows (part 11). No automatic issue: the operator files intake issues by hand after triage, as today.

**Why:** the mailbox is already where D5 and D7 keep raw evidence and reporter identity, so the form adds a channel into it and no second store of personal data. A Worker that also files an artifacts-only issue in the private repo would need a repo-write GitHub token stored at Cloudflare, and it would have to defang arbitrary reporter text (D8), which no Worker-side heuristic does reliably: a missed live URL in an issue is exactly what D8 forbids. That some unrelated Workers in the same account turn form submissions into GitHub issues changes neither reason; their pattern is not adopted.

**Rejected:**

- Email only: the operator's reasons against `mailto:` and against copying an address into another client (part 13).
- A Worker that writes R2 or KV: a second store of personal data next to the mailbox, with its own retention and access rules.
- Third-party form services: a request to a third party and its script or redirect on the site (D9).
- A same-origin path through proxied Pages DNS: Cloudflare would see every page view, and proxying changes how GitHub Pages issues its HTTPS certificate.
- A `*.workers.dev` hostname: a shared domain that is not the site's own, and Email Service needs the zone on Cloudflare DNS anyway.
- Cloudflare Pages Functions: it moves the site's hosting, which D4 decides.
- An automatic issue from the Worker: the two reasons above.

### 2. Language and runtime (STOP 1 decision 2)

A JavaScript ES module, `worker/intake.js`, one file, no imports except the runtime's `cloudflare:workers`. Tested under the pinned `workerd` release binary (PR 2).

**Why:** every API the Worker touches is a JavaScript API of the runtime: `Request.formData`, the Durable Object class, the Rate Limiting and `send_email` bindings and `crypto.subtle`. One reviewed file with no dependency graph is the pattern of the site's scripts (ADR-0005 part 5, one pinned source per script), and `workerd` is the open-source runtime that production runs, shipped as a single binary that needs no npm (D3).

**Rejected:**

- (a) workers-rs: its `worker-build` fetches esbuild from the npm registry, which D3 forbids on a developer machine, and its crate graph is far larger than a program of about 400 lines.
- (b) A std-only Rust core compiled to WebAssembly: a Durable Object class must be a JavaScript class and the runtime APIs above are JavaScript, so Rust would own only the byte and string checks, about 100 lines, behind a hand-written pointer and length interface. That adds a bug class the JavaScript version lacks, and the shipped binary is a file no review reads, against one reviewed, pinned source per script.
- (c) A Python Worker: its CLI `pywrangler`, needed to run one locally and to deploy it, requires Node (Python Workers docs, Context), which D3 forbids on a developer machine, and the runtime is CPython compiled to WebAssembly, a binary no review reads.
- (d) Miniflare or wrangler for the tests: npm (D3).
- Revisit trigger for Rust: the Worker starts parsing image formats, for example to strip EXIF metadata.

### 3. Anti-spam and quotas

D5 named Turnstile and D9 forbids third-party scripts; this part reconciles them: no widget. The checks run in this order, cheapest first, and each later one runs only when the earlier ones passed:

1. One WAF rate-limiting rule on the path `/submit`, before the Worker runs (Numbers).
2. `Origin`: absent, or exactly `https://interviewscam.com`. Anything else, `null` included, gets `#not-accepted`. A browser sends `Origin: null` for a cross-origin POST whose referrer policy is `no-referrer` or `same-origin`, so such a policy on the form pages would refuse every real submission. The site sets no referrer policy today (Pages sends no `Referrer-Policy` header, and no template sets one), so browsers use their default, `strict-origin-when-cross-origin`, and send `Origin: https://interviewscam.com`. **PR 3 obligation (fix round 1 of PR 2):** PR 3's render rule for the intake form refuses, on `/report-a-scam/` and `/corrections/`, a `rel` on the form that holds `noreferrer`, any `<meta name="referrer">`, and a `referrerpolicy` attribute on the form or a submitter. `hugo.toml` stays closed-world, so no config key can add one, and the PR 4 live test's real-browser submission proves the outcome.
3. A Rate Limiting binding keyed by the limiter key (part 11), a burst gate in front of the Durable Object. By the docs it costs no Durable Object request and no row written; PR 4 confirms that it is accepted on the account's plan and adds no Durable Object requests (part 12 step 9). If it is not available on Workers Free, the Durable Object limits alone, and the Durable Object requests per IPv4 address rise to the WAF's 43,200 per day, so 3 addresses can use them up; that stays inside option A's accepted exposure. That mode is explicit, never a silently missing binding (fix round 1 of PR 2): `tools/intake.py deploy --without-rate-limiter` uploads a `plain_text` binding `RATE_LIMITER_ABSENT` = `refused-by-cloudflare` instead of the Rate Limiting binding, `verify --without-rate-limiter` checks exactly that set, and the Worker skips the burst gate only when the binding is absent and that marker is present. With neither, every submission ends as `#error` (code `E_BURST_MISSING`), which `verify` and the live test report. The PR 4 body records which mode was deployed.
4. The per-client limit, the per-client daily mail cap and the global daily cap in one Durable Object, `IntakeLimiter` (Numbers). The Durable Object writes a row only for an attempt it counts: an attempt that arrives when the key's window is already full is refused after a read, with no write, so a refused source costs reads (5 million per day on Free), not rows written.
5. A honeypot field `website` inside a `<div hidden>`, read after the body is parsed. Any non-empty value, or a missing field, means no mail and a redirect to `#not-accepted`. The submission is rejected, not silently dropped, so a human who somehow fills it is told to use email instead; a silent drop could lose a D7 notice.

**Why:** a form without a widget gets bot traffic, and every layer above costs the visitor nothing: the WAF rule stops a flood from one address before the Worker runs, the Origin check stops cross-site posts, the binding stops a burst from one network before it costs a Durable Object request, the per-client limit bounds the parsing one network can cause, the per-client mail cap stops one network from filling the global cap alone, the global cap bounds the mailbox, and the honeypot stops form-filling bots. Writing only counted attempts bounds the rows one key can write (Numbers), which the shared account's 100,000 rows per day on Free needs.

**Weak point:** a targeted attacker who reads the form defeats the honeypot and the Origin check; the limits then bound the damage per source, and the address on the form page stays as a channel (part 6). Many sources are not bounded by any per-source limit (below).

**Shared quotas on Workers Free (operator decision, STOP 2, 2026-11-11: option A).** On Workers Free the daily quotas are per account, so the intake and the unrelated Workers share them. With the bounds above (Numbers, "Quota bounds per source"):

- The 100,000 daily Worker requests: the Free WAF counts by IP, with no documented IPv6 prefix grouping, so it holds one IPv4 address to 43,200 requests per day, and three addresses (129,600) can use the quota up. One IPv6 host that rotates addresses inside its /64 is not held by the WAF at all and can use it up alone. The binding and the Durable Object run inside the Worker, so they cannot reduce Worker requests.
- The 100,000 daily Durable Object requests: one key (a /64 or a /32) causes at most 9,073 per day per Cloudflare location (8,640 through the binding, at most 288 `reserve()`, `refund()` and notice calls, and at most 145 alarm runs), so 12 keys in one location can use them up, and fewer when one source reaches several locations.
- The 100,000 daily rows written: one key causes at most 440 per day while sends succeed (1,016 if every send fails), so it takes 228 keys (99); the 5 million daily rows read run out first, at about 26 keys (Numbers).
- In the explicit no-binding mode (step 3 above) nothing sits between the Worker and `attempt()`, so one key's Durable Object requests follow its Worker requests: up to 43,200 a day for an IPv4 address held by the WAF (43,633 with its `reserve()`, `refund()` and alarm calls), so 3 addresses use up the 100,000 Durable Object requests, the same 3 that use up the Worker requests; one IPv6 host rotating inside its /64 is held by neither and uses up both alone. The Worker requests therefore stay the first limit (or a shared one), and option A's accepted exposure is unchanged (Numbers, fix round 2 of PR 2).
- The 50 daily mails: one key mails at most 3 per day, so it takes 17 keys to pause the form.

When a Worker or Durable Object quota is used up, the intake fails until 00:00 UTC (Cloudflare's Error 1027 page, or `#error` from the Worker, which fails closed when the Durable Object fails), and so do the unrelated Workers that need the same quota. No setting on Workers Free closes this: per-source limits cannot bound many sources, and the only IPv6-aware counting (the binding and the Durable Object) runs after the Worker request is already spent.

**Decision: option A.** The intake stays on Workers Free in the existing account shared with unrelated Workers, and the operator knowingly accepts the exposure above, the outage of the unrelated Workers included. The channel degrades and is not lost: the address stays as plain text on both form pages and on `/not-sent/`. Until milestone 6 the site has no public audience (Context), so a flood is unlikely to find the endpoint; that mitigation ends at the M6 Launch, and from then on the exposure is permanent.

If step 2 of the cutover finds the account already on Workers Paid (chosen for the unrelated Workers, not for the intake), the daily quotas do not apply and option B's flood cost applies instead; step 2 records which.

**Rejected (quotas):**

- **B. Workers Paid** ($5 per month for the whole account): no daily Worker request limit and no daily Durable Object limits, so a flood costs money instead of availability, and that cost is linear in the flood with no documented hard spend cap. Ten IPv4 sources held by the WAF for a whole month: 10 × 43,200 × 30 = 12.96 million Worker requests, 2.96 million over the included 10 million at $0.30 per million, $0.89; and 10 × 8,640 × 30 = 2.59 million Durable Object requests, 1.59 million over the included 1 million at $0.15 per million, $0.24; about $1. One IPv6 host rotating inside its /64 at about 100 requests per second for a month (an assumed rate, so an estimate): 100 × 86,400 × 30 = 259.2 million Worker requests, 249.2 million over the included 10 million, $74.76, so about $75, plus CPU time over the included 30 million CPU milliseconds at $0.02 per million (about $4.60 if each refused request takes 1 ms, also an estimate); its Durable Object requests stay bounded per key by the binding. The operator chose a loss of availability over an open-ended bill.
- **C. A dedicated Free Cloudflare account for interviewscam only:** at $0 it would isolate the daily quotas from the unrelated Workers, confine the account-wide deploy token to this site and make the member condition of part 9 hold by construction. The operator rejected it to keep the existing account (STOP 1 amendment, confirmed at STOP 2).

**Rejected (anti-spam):**

- Turnstile, reCAPTCHA and every other widget: a third-party script (D9).
- The Rate Limiting binding as the only limiter: approximate, per location and limited to 10 or 60 s periods, so it cannot express an hourly limit or a daily cap. It stays as a burst gate.
- KV counters: eventually consistent, so parallel requests read a stale count.
- A JavaScript proof of work: the form must work without JavaScript.
- Counting refused attempts with a write (the plan's first form): one source held by the WAF to 43,200 attempts per day would write up to 129,600 rows (insert, delete and alarm), more than the account's 100,000 on Free.

### 4. Uploads

PNG, JPEG, GIF and WebP only, detected by their magic bytes:

- PNG: `89 50 4E 47 0D 0A 1A 0A`.
- JPEG: `FF D8 FF`.
- GIF: `GIF87a` or `GIF89a`.
- WebP: `RIFF`, 4 bytes, then `WEBP`.

The client's MIME type is ignored, and its file name never names the attachment: each file is re-attached as `evidence-<n>.<ext>` with the detected type. The mail body lists each original file name as context for the moderator, with the body's control stripping and scheme rewrite (part 7), cut to 100 characters (Numbers). A count cap and a total size cap (Numbers), no per-file cap. A file part with an empty file name and size 0 (the browser's "nothing chosen" part) is ignored. The page tells reporters to send PNG or JPEG.

**Why:** screenshots are the evidence D7 asks for. Detection by bytes, not by the client's claim, keeps executables and documents out of the operator's mailbox. The total bounds memory, CPU and message size; a per-file cap would only reject one large screenshot that the total admits. SVG is excluded because it is active content. HEIC and AVIF are excluded because they are not screenshot formats and the operator's mail client may not render them.

**Rejected:** a per-file cap (above); accepting any type the client names (a renamed executable passes); SVG (active content).

### 5. Fields per channel

These names are load-bearing (PR 2 and PR 3 read them). `channel` is a hidden field, `report` or `correction`.

- `report`: `name` (required), `contact_start`, `details` (required), `headers`, `email` (required, STOP 1 decision 3), `files`, `website`.
- `correction`: `page_url` (required; it must parse with the WHATWG URL parser to the origin `https://interviewscam.com` and hold no `White_Space` at all, because a copied page URL has none and the parser would percent-encode an inner space and carry a second URL into the subject: fix round 1 of PR 2), `request` (required), `own_name` (checkbox, value `yes`), `email` (required), `files`, `website`.
- The set is closed: an unknown field, or a single-value field sent twice, gets `#not-accepted`.
- Lengths are counted in UTF-16 code units after CRLF and CR become LF. That is the unit HTML `maxlength` uses, so a value within `maxlength` is never refused as too long.
- A required value is empty when nothing is left after trimming Unicode `White_Space` plus U+200B, U+2060 and U+FEFF.
- `email` must match the HTML "valid e-mail address" grammar, the one the browser uses for `type="email"`, and be at most 254 characters.

**Why:** a closed set and fixed caps give each field one meaning the moderator can rely on and bound the mail. The reply address is required because the operator acknowledges every submission and identity-dependent requests wait for the answer (part 8); without it such a request could never be verified. Counting as the browser counts and validating as the browser validates means the server refuses what the browser's own validation accepted in one case only: a required field that holds nothing but whitespace or invisible characters, which HTML `required` lets through (it fails only an empty value) and the Worker answers with `#missing-field`.

**Rejected:** an optional reply address (decision 3: an unverifiable request); free-form extra fields (no fixed meaning, unbounded mail).

### 6. Responses

- Every outcome the Worker's code decides is a `303 See Other` to `https://interviewscam.com/sent/` or `https://interviewscam.com/not-sent/#<id>`; 303, not 302, because a POST must become a GET.
- The `<id>` comes from a closed set: `too-large`, `too-many-files`, `not-an-image`, `missing-field`, `too-long`, `bad-address`, `bad-page-url`, `too-many-attempts`, `paused`, `not-accepted`, `error`.
- The redirect target is covered by `form-action 'self'`, whether or not a browser applies `form-action` to redirects.
- Headers: `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. No `Set-Cookie`, ever.
- A method other than POST gets `405` with `Allow: POST` and an empty body. A POST to another path gets `404` with an empty body.
- Any exception the code catches gets `#error`; the code itself never answers 500 and never shows a stack trace.
- The Worker holds no copy: `/not-sent/` explains each case, says that chosen files must be picked again after going back, and always shows the address as plain text.

**Outcomes that never reach the Worker's code** (Context), each answered by a Cloudflare page that shows neither the address nor `/not-sent/`:

- Error 1102: the request ran over the CPU limit, or over the memory limit of its isolate, which concurrent requests share (Numbers, "Memory per max-size request").
- Error 1027: the account's daily Worker requests on Workers Free are used up (part 3).
- The WAF rule's block response, for a sixth request in 10 s from one address.
- `413` for a body over the zone plan's limit (100 MB on Free), far above `INTAKE_MAX_BODY`.

Closure: the form pages show the address as plain text next to the submit button, with one sentence that says to send the report there if sending fails (PR 3 copy, under the D7 wording review). The browser's Back button returns to that page from any of these errors. PR 4's live test records which of these pages it met.

**Why:** the Worker then emits no text at all. Every word a reporter reads from the Worker lives on a static page of the site, under `literals`, `render`, the HTML checker and Lighthouse, and the D7 wording review covers it like any other page. Where Cloudflare answers instead, the form page itself already carries the way out.

**Rejected:** a Worker that renders its own result pages: text outside every check, served from a second origin with its own CSP. Custom Cloudflare error pages: text outside every check, served by Cloudflare instead of the site.

### 7. Mail

- `from: intake@interviewscam.com`, no `to` (the binding's `destination_address` applies), `replyTo` the validated `email`.
- Text only, no HTML part.
- Subject: `Report: <name>`, `Correction: <page_url>`, or `Correction, own name: <page_url>` when `own_name` is set, so the SPEC §6 hide-first case stands out in the mailbox. The subject uses the raw submitted value, after the stripping below, not the WHATWG serialization of the URL: percent-encoding can grow a non-ASCII path up to 9 characters per code point, which would break the 998-character bound of `page_url` (Numbers).
- Subject values are stripped of C0 and C1 controls, bidi controls (U+202A to U+202E, U+2066 to U+2069) and zero-width characters (U+200B to U+200F, U+2060, U+FEFF), and whitespace is collapsed. Then they get the body's scheme rewrite (below), which keeps the length, so the 998-character bound holds (fix round 1 of PR 2: a report name carried a live URL into the subject).
- The body keeps the reporter's text verbatim with two changes, and lists the original file names (part 4) under the same two changes. The single-line fields (`name`, `contact_start`, `email`, `page_url`) and the file names also have every `White_Space` character replaced by a space: a browser strips line breaks from text, email and url inputs, so only a hand-made request sends one, and on its own line it could forge a label line such as `Own name: yes` (fix round 1 of PR 2 replaced TAB and LF; fix round 2 widened it to the whole set, because U+0085 is a line break to line-splitting readers and U+2028 and U+2029 are mandatory breaks in UAX #14, so a mail view can start a new line at each). C0 controls other than TAB and LF are removed. URL schemes are rewritten: `http://` becomes `hxxp://`, `https://` becomes `hxxps://`, `ftp://` becomes `fxp://`, case-insensitively and idempotently, and a header line states that rewrite.

**Why:** the subject lines match the ones the email channel already asks for, so both channels sort alike. The scheme rewrite makes a pasted live URL inert in the operator's mail client. Bare domains stay; that is no new gap, because today's email channel delivers them the same way and the page asks for defanged text (D8).

**Rejected:** an HTML part (markup from reporter text in the operator's client); defanging bare domains in the mail (a heuristic that changes evidence and still misses forms; the page instructs reporters instead).

### 8. Verification before acting (D7; STOP 1 decision 3)

A typed reply address is unverified: anyone can type anyone's address, while an emailed report's sender is at least checked by its provider. So the reply address is required on both forms, and the moderator acknowledges every submission by replying to it.

**Notices, identity and independence (operator decision, STOP 2, 2026-11-11: approved as drafted).** It keeps decision 3's reply requirement and narrows what the reply gates.

- **A notice whose substance can be checked is acted on, answered or not.** A notice that a page is wrong in a way the moderator can check against the record's own evidence and cited sources is reviewed on its merits whether or not the requester answers the acknowledgment. Examples: a wrong artifact, a wrong D6 state, a source that does not say what the page cites it for, a live attacker URL. The outcome goes to the given address. Who sent it does not change what the evidence shows, and D7's hosting basis rests on acting on notices.
- **The reply gates only identity-dependent requests**, where the outcome depends on who asks:
  - a person's own name (the SPEC §6 hide-first rule);
  - a request that relies on being the named company, verified by a reply from an address on the company's own domain or by other evidence;
  - a request under data protection law (GDPR Art. 12(6) lets the controller ask for proof of identity);
  - the standing to have one's own report or evidence withdrawn.
- **The own-name hide is bounded.** The name is hidden at once, before the review. If the requester has not answered within 28 days of the receipt of the request (Numbers), the request is decided as not verified and the name returns. A further unanswered request for the same name does not hide it again; an answered one does. A verified request goes on to the review the SPEC describes.
- **Independence is judged by the evidence, not by addresses.** A form report counts toward `independent_reports` only after the reporter answers. An answer proves control of an address, nothing more: one person with ten mailboxes can answer ten times. So reports count as independent only when their evidence is independent: different received messages (different sending servers or dates in the headers), different contact messages or invitations, screenshots that are not copies of each other. Reports that share their evidence, or that the moderator links by wording, files or timing, count once. The count stays the moderator's D7 judgment, and the D7 label states only the count.

**Why:** D7 publishes nothing without review, and the count of independent reports is a public claim. A competitor must not remove a record by typing someone else's address, which the identity gate prevents, while a precise notice about a checkable error must not wait on a reply that may never come, because the page stays up during review either way and the evidence decides. The 28-day bound keeps an impostor's hide short and keeps the decision inside the one month the controller has to answer (Numbers).

**Weak points:** a third party's address typed into the form receives one neutral acknowledgment. One person who captures separate evidence of separate contacts still counts as several reporters, because those are several real contacts. An impostor can hide an active persona name once, for at most 28 days.

**Rejected:** acting on an unanswered identity-dependent request (a forged requester); ignoring an unanswered notice whose substance is checkable (a correct notice would never be acted on); counting answered addresses as independent reports (one person, many mailboxes); an unbounded hide (an impostor hides a name for good); a verification link or auto-reply sent by the Worker (it would make the Worker a mail relay for any address typed into the form; Consequences).

### 9. The endpoint origin under D9 and SPEC §8

The endpoint is first-party: a subdomain of the site's own registrable domain, run by the same controller. A form submission is a navigation the visitor starts, like `<a href>`, not a request the page makes. D9 and §8 ("none in the built site") therefore hold unchanged.

**Condition:** "run by the same controller" holds only while the operator is the only member of the shared Cloudflare account with rights over Workers, because any such member can change the Worker's code and read submissions (part 10 (b)). The cutover checks it (part 12 step 2). If another member holds Workers rights, the cutover stops until those rights are removed or scoped away from Workers; if that cannot be done, the endpoint is code a third party can change, D9's first-party claim fails, and the account decision goes back to the operator.

- No page fetches anything from the intake origin; every request-scan rule of `site` keeps refusing it.
- Only `<form action>` may name the intake origin, only as exactly `INTAKE_ACTION`, and only on the two intake pages (PR 3).
- `params.csp` `form-action` is exactly `'self' https://intake.interviewscam.com`. `'self'` stays for the Home search form, which submits GET to `/a-z/`.

**Why:** D9 protects visitors from requests they did not ask for and from code a third party can change. A submit they press, to the site's own domain, on code only the operator can change, is neither. Pinning the one action on the two pages keeps every other page exactly as strict as before.

**Rejected:** loosening `leaves_origin` for the intake origin (every request-scan rule would admit it); a wildcard or a path in `form-action` (wider than the one origin the form needs).

### 10. Source, pinning and deploy

- The source lives at `worker/intake.js` in the public code repo, so it holds no secret. Its SHA-256 is pinned in `tools/sitecheck.py`, so every Worker change is a `tools/` change and gets the safety-net review.
- The operator deploys from their own machine with `tools/intake.py deploy`. The tool refuses to run under `CI` or `GITHUB_ACTIONS`, on a dirty tree, on a HEAD other than `site/main`, or when the source differs from its pin.
- `tools/intake.py verify` checks what decides where submissions go, not only the code. It downloads the deployed script and compares it with the pin, and it reads the script's settings ("Get Worker Script and Version Settings", Context) and compares them with the expected values: the bindings, each with its type and the `send_email` binding's `destination_address`; no tail consumers; Logpush off; observability with invocation logs off and no export destination. It also reads the custom domain list and checks that `intake.interviewscam.com` maps to `interviewscam-intake` alone, and it reads the zone's Worker routes and fails on any route whose pattern covers that host, because a route could send its requests to another script (the Routes docs: a route takes precedence over a Custom Domain on the same hostname). A pattern may begin with `http://` or `https://` and a leading `*` matches any prefix, and hosts compare without case, so the check strips the scheme and folds the case first (fix round 2 of PR 2). It also reads the active deployment (fix round 2 of PR 2): the API reference's List Worker deployments ("the first deployment in the list is the latest deployment actively serving traffic") must show exactly one version at 100 %, because a split deployment sends part of the traffic to another version and a version left at 0 % can still be selected by any client with the `Cloudflare-Workers-Version-Overrides` header (the version overrides docs: "even those set to serve 0% of traffic"); that version must be the first of List Worker Versions (the latest upload), so the content and settings read above describe the deployed version whichever version those endpoints answer for; and Get Version's `resources.bindings` and `resources.script_runtime.compatibility_date` of that version must be the expected ones. Fix round 3 of PR 2 added four more checks and one action:
  - The deployment's `strategy` must be `percentage`. That is the only strategy the API reference documents, and the only one whose traffic split `verify` can read; any other value is a deployment it cannot judge, so it fails.
  - Its `code_update_strategy` must be absent or `{"mode": "immediate"}`. A `deferred` update lets a busy Durable Object keep an earlier version's class code for up to `max_delay` seconds (at most 86,400). When the field is absent the docs say only that "the default strategy applies", without naming it, so PR 4 records the value the live deployment reports.
  - The compatibility date is compared by its date part, so `YYYY-MM-DD` and the `YYYY-MM-DDT00:00:00Z` form of the Get Version example both pass, and any other form fails.
  - A route pattern is also read as a whole glob (`*` matches any run of characters, Routes docs), so `intake.interviewscam.com*` covers the intake path too.
  - The workers.dev route and the Version (preview) URLs must be off. `deploy` turns both off (Post Worker Script Subdomain, `{"enabled": false, "previews_enabled": false}`, Workers Scripts Write), and `verify` reads them (Get Worker Script Subdomain, which Workers Scripts Read accepts). On a workers.dev host, outside the zone, the zone's WAF rule does not apply, so one IPv4 address could use up the Worker and Durable Object quotas alone, against the per-IPv4 bounds of part 3. A Version URL would also keep earlier versions invocable with their own code.
- **PR 4 operator check (fix round 3 of PR 2):** a zone rule that is not a Workers route can still divert the form, because a redirect rule runs before Workers and a browser re-POSTs the body on a 307 or 308. Reading the zone's rulesets would need a further zone read grant on a token that should stay narrow. So at the cutover, and whenever `verify` runs after a change to the account's members or tokens, the operator checks two places for any rule whose expression or URL matches `intake.interviewscam.com`: the dashboard's zone page Rules > Overview, with its Redirect Rules list and any Page Rule with a forwarding URL; and `GET /zones/<zone>/rulesets/phases/http_request_dynamic_redirect/entrypoint`. The PR 4 body records the result, and the live test's `live_headers` row fails while such a rule exists. Fix round 1 of PR 2 tightened the bytes check too: when the deployed content comes back as several modules, it must be exactly one module, `intake.js`, and an entrypoint header, when the answer carries one, must name `intake.js`, so a foreign main module next to the pinned `intake.js` fails. The tool prints the account ID, the zone ID and the destination address only as placeholders, because its output may be pasted into the public PR 4 body. At the same points the operator checks in the dashboard that the Email Routing rules and destination addresses are the expected ones, because the deploy token does not read Email Routing.
- The tool hard-codes the script name `interviewscam-intake` and tags the script `interviewscam-intake`. It refuses to upload when a script of that name exists without that tag, so a typo or a name clash can never overwrite an unrelated Worker.
- The token is read from `CLOUDFLARE_API_TOKEN` or a `getpass` prompt and is never written, logged or printed. The account ID, the zone ID and the destination address are prompted too and never stored in the repo. The tool never creates a token.
- Deploy language: Python standard library (`urllib`, `ssl`, `json`), like the existing tools.

**The deploy token is made in the dashboard.** The operator creates it in the Cloudflare dashboard, logged in with 2FA, for one deploy session: start date today, end date the next day (the dashboard sets both at 00:00 UTC, so the token expires at the next 00:00 UTC, at most 24 h after it is made), and a client IP filter of the operator's current address. No token that can create tokens ("Create additional tokens") is ever made, because it could create tokens with access to any of the operator's resources, a credential far wider than the deploy grant. The operator revokes the deploy token right after the session; the tool prints that reminder.

**Token scope (STOP 1 amendment).** The operator asked for a token limited to this zone and this one Worker. The public docs read for this ADR (Context) document no token resource for a single Worker: Workers Scripts Edit is an Account permission, and token resources are User, Account and Zone. The API reference names "Individual Workers" permissions that no other page explains. This is not settled by the docs, so it is an **operator verification step** before the first deploy (PR 4, before the token is made): in the dashboard's token form, or with the permission-groups list of the account (`GET /accounts/{account_id}/tokens/permission_groups`, with a read-only token made for that and revoked after), look for a permission group or a resource that applies to one Worker script; record the result in the PR 4 body.

- If a per-script scope exists and covers everything a deploy does (upload, the Durable Object class migration, the secret, the Rate Limiting and `send_email` bindings, the custom domain, the script settings that `verify` reads), the token uses it alone, and no account-wide Workers permission is granted.
- If a per-script scope exists but covers only part of that, the first deploy (which creates the Durable Object class, sets the secret and attaches the custom domain) uses the account-wide grants below; every later deploy uses the per-script token alone when it covers that deploy's steps, and falls back to the account-wide grants for that one session when it does not. `verify` uses the per-script scope when it can read the settings.
- Otherwise these are the narrowest grants:
  - Account policy: this account only (`com.cloudflare.api.account.<ACCOUNT_ID>`), Workers Scripts Edit only, nothing else at account level. It covers the upload, the bindings, the secret and the custom domain (the API reference lists Workers Scripts Write for Attach Worker Domain).
  - Zone policy: `interviewscam.com` only (`com.cloudflare.api.account.zone.<ZONE_ID>`), Workers Routes Edit, for the custom domain. If the first deploy in PR 4 attaches the custom domain without it, PR 4 narrows this grant to Workers Routes Read and amends this part, but never drops it: `verify` reads the zone's Worker routes (`GET /zones/<zone>/workers/routes`, whose accepted permissions are Workers Routes Write or Workers Routes Read, API reference "List Routes"), and it runs at the end of every deploy and in every branch of this part, a per-script scope included, so without the zone grant every `verify` would fail with HTTP 403 (fix round 2 of PR 2).
- The account-wide grant is contained in four ways: (1) validity to the next 00:00 UTC, at most 24 h, set in the dashboard; (2) client IP filtering to the operator's current address; (3) revocation right after the session; (4) the tool can address only one script.

**Shared-account blast radius (STOP 1 amendment).** The account is an existing account shared with unrelated Workers. Three directions:

- (a) From this deploy outward. A token stolen during its validity window could rewrite the unrelated Workers, including any that hold their own secrets. Containment: the window, the IP filter and the revocation above, and no token-creating token. Under a per-script scope that covers the deploy, (a) disappears.
- (b) From the account inward. Any account member with Workers rights, and any long-lived token of the account with Workers Scripts Edit, could rewrite the intake Worker, change its bindings and read reporters' submissions. Containment: at the cutover the operator checks that no other member holds Workers rights (part 9) and reviews the account's API tokens; every token with Workers edit gets a validity limit or is revoked. `verify` runs after every deploy, in the PR 4 live test, before the M6 launch, and after any change to the account's members or tokens.
- (c) Shared Free-plan quotas: part 3, "Shared quotas on Workers Free".

**Why:** a deploy is rare and needs the most powerful credential in the design, so it happens where the credential lives for the shortest time and nothing else can read it, and the dashboard makes it without a wider credential in between. The pin plus `verify` makes "the code that runs, and the place it sends submissions, are the reviewed ones" a check, not a hope, which matters more in an account other parties can write to.

**Rejected:**

- A CI deploy job: it would put a Cloudflare token into GitHub Actions of a public repo, where a compromised action or a workflow change could read it.
- A token created through the API: it needs a token-creating token first (above).
- A long-lived deploy token: it widens exposure (a) to every day of the year.
- A `verify` that compares only the script bytes: a changed binding or a tail consumer sends submissions elsewhere while the bytes still match.
- A dedicated Cloudflare account: the operator declined a new account at STOP 1.
- Rust for the deploy tool: its standard library has no TLS client, so it would need a crate stack or a call out to `curl`.

### 11. Privacy and logs

- The limiter key is HMAC-SHA-256 under a 32-byte secret, `LIMITER_KEY`, over the IPv4 /32 or the IPv6 /64 of `CF-Connecting-IP`. An IPv4-mapped IPv6 address is read as IPv4. The raw IP is never stored or logged by the Worker; the Rate Limiting binding gets the keyed hash as its key, not the IP.
- Limiter rows are deleted when they expire, 3,600 s after the attempt they record: the Durable Object keeps its one alarm set to the earliest expiry among its rows, and the alarm handler deletes every expired row and sets the alarm to the next expiry (alarms run at least once, at or after their time; an access also deletes expired rows). So a limiter row holds a keyed IP hash for about 1 hour. The per-client daily mail rows, which hold the keyed hash too, and the global daily counter are deleted at the end of the UTC day by the same alarm, so the keyed hash of a client that sent mail is kept up to 24 h (Numbers).
- Workers Logs on, invocation logs off. Custom log lines are `intake event=<code>[ code=<E_...>]` only.
- Email preview off for the domain (PR 4 verifies it).
- The Email Routing activity-log retention is verified in PR 4 and stated on the privacy page.
- Cloudflare's own logs, outside the Worker, keep client IPs. The intake hostname is proxied (a Workers Custom Domain), so Security Analytics keeps sampled logs of all its traffic, form POSTs included, with the source IP, user agent and path, for up to 31 days on Free, and shows every request (its "Raw logs" view) when fewer than 100 match. Security Events keeps every request the WAF rule blocks for 31 days, with the client IP (Context). Neither can be switched off for a proxied hostname; the privacy page names both, and PR 4 records their retention on the account.

**Why:** the limiter needs a stable key per source for one hour and nothing more; a keyed hash cannot be reversed by enumerating the 2^32 IPv4 addresses, which a plain hash can. Event codes are enough to debug the Worker and carry no personal data. Email preview would keep every submission, attachments included, a second time at Cloudflare for about 7 days. Cloudflare's request logs are the price of a proxied endpoint, which the Worker and the WAF rule need; the privacy page states them instead of claiming that no IP is kept.

**Rejected:** a plain hash of the IP (reversible by brute force); invocation logs (they record request metadata per call); leaving Email preview on (a second copy of every submission); dropping the WAF rule to avoid its log (one address could then use 100,000 Worker requests a day, part 3, and Security Analytics would still keep the requests); an hourly sweep instead of an alarm per expiry (rows would live up to 2 h).

### 12. DNS and Email Routing cutover order (SPEC §9)

PR 4's runbook, in this order. T_NS is the TTL of the parent's NS records for the domain and T_MX the TTL of the forwarding MX records at Namecheap, both measured with `dig` on the day (2026-11-11: T_NS 172,800 s, T_MX 1,800 s, no DS). T_MX' is the TTL of the forwarding MX records as the Cloudflare zone serves them after the import, measured with `dig` against Cloudflare's nameservers before step 5, or, if they do not answer for the zone while it is Pending, right after step 5 and before step 6 (the formula of step 7 does not change). t0 is the time of the nameserver switch (step 5), t6 the time Email Routing's MX records replace the forwarding MX records in the Cloudflare zone (step 6).

1. **Inventory.** Export the Namecheap DNS records. Note whether `report@` forwarding is active, measure T_NS, T_MX and whether the parent has a DS record.
2. **The account.** Verify that the login has passkey or hardware-key 2FA; check that no member other than the operator holds Workers rights (part 9) and that every member is needed and has 2FA; review the API tokens (part 10 (b)); record the Workers plan tier (the operator's STOP 2 decision keeps the intake on Workers Free, part 3; if the account is already on Workers Paid, record that option B's cost exposure applies instead). Add the zone. Review the imported records: keep the Namecheap forwarding MX records and their SPF record while forwarding is active, so resolvers that already follow the new delegation still reach the forwarder; GitHub records DNS-only; the Pages verification TXT record; no wildcard.
3. **Ask Namecheap first.** Before the switch, the operator establishes (Namecheap documentation or support, recorded in the PR 4 body) whether Namecheap's forwarding keeps forwarding for the domain, and whether its nameservers keep answering for the zone, once the domain uses other nameservers.
4. **DNSSEC.** If the parent has a DS record: remove it at Namecheap and wait the DS TTL (measured at the parent).
5. **Switch.** Set Cloudflare's nameserver pair at Namecheap and note the time t0. Wait for the zone to show Active.
6. **Email Routing.** Add and verify the destination address and create the rule `report@` to that destination; Cloudflare's MX, SPF and DKIM replace the forwarding MX in the Cloudflare zone; note that time, t6. A test mail from an outside account must arrive and show "Forwarded" in the Activity log.
7. **Keep the old forwarder.** Leave the Namecheap forwarding configured until both hold: step 6 passed, and max(t0 + T_NS + T_MX, t6 + T_MX') + max(T_MX, T_MX') has passed (Numbers). Then remove it.
8. **DNSSEC again.** If step 4 removed a DS: enable DNSSEC at Cloudflare and add its DS at Namecheap.
9. **Worker.** Email preview off; the operator verification of the token scope (part 10); create the token in the dashboard; deploy, `verify`, create the WAF rule. Confirm the Rate Limiting binding on the account (Context, part 3): the upload with the binding is accepted on the account's plan, and in the live test the Durable Object requests in the Workers metrics equal the attempts the binding passed, so the binding adds none; record both in the PR 4 body, and if the binding is refused, deploy without it and record the higher Durable Object bound of part 3. Then the live test; `verify`; revoke the deploy token. The CPU series, the memory series and the live proof of the per-client daily mail cap follow on the same or later UTC days (Numbers, "Measurement key-days"); the two series are each read with a read-only analytics token that is revoked after the reading, and the cap proof needs no token. Record the retention of Security Analytics and Security Events on the account (part 11).

**Why:** a DS record left in place while the nameservers move breaks resolution for validating resolvers, so it goes first and its TTL is waited out. Two kinds of resolver can still send mail to the old forwarder. One that kept the old delegation (up to T_NS after t0) can fetch the Namecheap MX through it and keep it for T_MX: until t0 + T_NS + T_MX. One that follows the new delegation gets the forwarding MX from the Cloudflare zone until step 6 replaces it and keeps it for T_MX': until t6 + T_MX'. The forwarder stays until the later of the two, plus the larger MX TTL as margin for resolvers that fetched just before a change. If step 3 finds that Namecheap stops forwarding, or stops serving the zone, as soon as the nameservers change, the window up to t0 + T_NS (48 h today) can delay mail but not lose it, as long as Namecheap's nameservers stop answering rather than answer without MX: a sender whose lookup fails retries for days (RFC 5321 §4.5.4.1 suggests a give-up time of at least 4 to 5 days). If they answer without MX, mail sent in that window can bounce. The cutover runs before milestone 6, while no published page carries the address (Context), so only the operator's own test mails can fall into that window; step 3's answer goes into the PR 4 body either way.

**Rejected:** switching nameservers and mail in one step (a resolution or delivery gap that nothing measures); removing the forwarder after 2 × T_MX alone (it ignores the delegation TTL, 48 h today); counting from t0 alone (a late step 6 leaves new-delegation caches on the forwarding MX until t6 + T_MX').

### 13. Why no `mailto:`

The operator's own reason, paraphrased (Replikanti/interviewscam#13, comment 6641084060): a `mailto:` link hands off to whatever mail app the operating system registered, often one the visitor never uses. The form is the convenient path, and the address stays visible as plain text to copy into the client the visitor actually uses. SPEC §7 and `site` rule (e) stay as they are.

**Why:** the goal of D5 is that a visitor who has evidence sends it. The visitor who uses a webmail client in the browser, often on a phone, is exactly the one a `mailto:` hand-off loses, and the form serves that visitor without leaving the page; the plain-text address serves everyone else and is the fallback when the form fails (part 6).

**Rejected:** a `mailto:` link next to the form (the hand-off above, and rule (e)).

## Consequences

- PR 2 (`worker/intake.js`, `tests/worker/`, `tools/intake.py`, the `INTAKE_*` constants, the Rate Limiting binding and the workerd pin) and PR 3 (the forms, `data/labels.toml`, the result pages, the CSP, `site` rule (a) and the check that every built page URL is at most 976 characters) are safety-net PRs; PR 3 and PR 4 are also content PRs, so they get `sdlc-reviewer` with QA and the operator's D7 wording approval at their STOP 2. PR 2's tests follow the bounds of this ADR: the body limit is `INTAKE_MAX_UPLOAD_BYTES` + 327,680, a refused attempt over a full window writes no row, the per-client daily mail cap is 3.
- The field names, `INTAKE_RESULT_IDS`, `IntakeLimiter`, the script name `interviewscam-intake` and the intake URL become load-bearing names; a rename changes the Worker, the constants, the forms and the result pages in one PR.
- A Worker change is a re-pin and a redeploy by the operator; `verify` (code, settings and custom domain) is part of every deploy, the PR 4 live test, the M6 launch and every change to the account's members or tokens.
- The privacy page is written only in PR 4, from the settings verified there.
- On Workers Free, many sources can use up the shared account's daily quotas, which takes down the unrelated Workers too; the operator accepted that at STOP 2 (part 3, option A), a permanent exposure from the M6 Launch on. The channel degrades but is not lost: both pages and `/not-sent/` always show the address, and the cap notice reaches the operator.
- `send_email`, the Rate Limiting binding and the Durable Object are emulated by workerd locally; the `send_email` stand-in refuses what the Email Sending docs say the binding refuses (a sender off the onboarded domain, a `to` other than the destination, no subject or one over 998 characters, more than 32 attachments, an attachment without content, file name, type or a disposition of `attachment` or `inline`, a message over 25 MiB). The pause notice is a subset of the live-tested message (`from`, `subject` and `text`, no `replyTo`, no attachments), so it is proven under workerd against those rules, not live, because a live proof would take 50 mails; a failed notice is retried and logged (Numbers, "Global cap"). The live test in PR 4 (fix round 1 of PR 2 adds the last three items) also sends one submission over HTTP/2 (`curl --http2`), one over HTTP/3 when the operator's curl supports it (`curl --http3`), and one from a real browser through the PR 3 form, each of which must reach `/sent/`, because the Worker refuses a request without `Content-Length` and the live suite's HTTP/1.1 client always sends one. It is the production proof for a subset of that suite: one mailed submission end to end, the rate-limit test (7 honeypot-filled attempts), `verify`, the result pages it meets, and the binding check of part 12 step 9; the per-client daily mail cap of 3 gets its own live proof on day 3 (row "Measurement key-days"). The rate-limit test predicts the first limited attempt from the key's earlier attempts in both windows, the binding's 60 s and the hour, the live test's mailed submission included, and the attempts of both tests are spaced at least 2.5 s apart, so at most 5 fall in any 10 s and the WAF rule, which blocks only a sixth, never answers in the Worker's place. The global cap of 50 is proven only under workerd, because a live proof would take 50 mails in one UTC day. The CPU and memory series stay under both caps by plan, so they test neither.
- Out of scope: any widget; an automatic issue; a Worker auto-reply (it would make the Worker a mail relay for any address typed into the form, which is the reason that stands; sending to arbitrary recipients would also need Workers Paid, which option A of part 3 keeps out); DMARC policy and replies sent as `@interviewscam.com` (offered to M6); defanging bare domains and stripping EXIF in the Worker; the Pages DNS records and enabling Pages (M6).
